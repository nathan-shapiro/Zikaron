# Zikaron — high-level design

> **Start here.** This is the entry point to Zikaron's design: what it is, why it is shaped this way, and
> where the detail lives. The full record of settled decisions and their rationale is §4; the detailed
> specs are indexed in §5. `FINDINGS.md` is the project's working memory — current state, open questions,
> references — and points here for design.

## 1. What Zikaron is

**Zikaron** (Hebrew/Yiddish זיכרון — "memory, remembrance") gives a coding agent the two kinds of project
knowledge that are not in its source code. **Tribal knowledge**, in the *memory store*: what nobody wrote
down, because it was learned by living through the work — how to build and test, which steps fail silently,
which env vars the integration tests need, which API is not safe to use yet and why, what was already tried
and how it failed. **Institutional knowledge**, in the *knowledge index* (D1 as amended,
`design/knowledge-index.md`): what the project did write down, indexed and returned as fragments with line
ranges.

Sharp scope line, set by the user (2026-07-31): ~~Zikaron is **not** a codebase knowledge base. Code
structure, symbols, and repo maps are handled by a **separate** system.~~ **— amended 2026-09-15 with
D1, and this paragraph did not follow it for a week.** The separate system that line delegated to was
kiro's built-in `knowledge` tool; Claude Code ships no equivalent, so the dependency disappeared
without the sentence ever becoming self-contradictory. **That separate system is now Zikaron's own**
(`design/knowledge-index.md`), and Zikaron holds **two** kinds of knowledge:

- **the memory store** — what is **learned by living through the work**, procedural and episodic, not
  derivable by re-reading the source. What `remember` accepts is unchanged by the amendment.
- **the knowledge index** — named corpora of text files the project already wrote, searched and
  returned as fragments with line ranges. **No authored content** — an agent can create, rename,
  refresh and remove a corpus, but nothing it writes becomes searchable text. No write policy, no
  consolidation.

The operational test that draws the line, and the one the write policy hands to the agent, governs the
**memory store** only: *could you learn this by reading the code?* If yes, it does not belong there. A
knowledge base has no such test — it is whatever corpus somebody points it at.

**Non-goals.** Emulating human psychology, affect, or personality for its own sake. Memory-science
mechanisms are welcome only where they buy measurable task benefit.

## 2. Shape of the system, in one page

**The memory store.** Two tiers in ~~one SQLite store~~ **`memory.db`**: a **journal** of unconsolidated
observations and a **long-term** tier of consolidated ones. Every record is `{uuid, gist, content}` plus
provenance and a version.
*(This section said "one SQLite store" and "four processes", and both were true until D1's amendment. A
store now also holds `knowledge/<uuid4>.db` per corpus, and the detached indexer is a fifth process. §1
directly above promised two kinds of knowledge while this section delivered one — the neighbour class,
between two sections of one page.)*

**Reading** happens two ways. A `userPromptSubmit` hook **pushes** the top five gists into context on every
user message, so the agent does not have to know it should ask. The agent then **pulls** — fetching full
content by uuid, or re-searching with its own keywords — through MCP tools. Retrieval is hybrid: BM25 over
FTS5 fused with dense vector search, because exact technical tokens demand lexical matching and paraphrase
demands embeddings.

**Writing** is the primary agent's own judgment, with **no extra LLM on the write path** — it records a new
journal entry, amends an existing memory, or does nothing, and authors its own gist. Amendment is how
staleness gets repaired: the agent that a memory misled is the one best placed to correct it.

**Consolidation** is the only extra LLM, and it runs off the hot path in a separate subagent the user
invokes. Code groups journal entries topically using retrieval as the adjacency function; the subagent
decides merge versus create versus discard.

**The knowledge index.** Named corpora of files the project already wrote, one SQLite database each
under `.zikaron/knowledge/`, registered in `memory.db`. **No authored content, no write policy, no
consolidation and no scope test** — an indexer walks the files, chunks them and stores their text
with line ranges, and the agent reads fragments back. *"No write path" was the phrasing here and
everywhere else this contrast is drawn — `FINDINGS.md` records which sites — and it is false as
stated: `add`, `rename`, `refresh` and `remove` are write paths
an agent calls, and `add` persists the agent's own name, description, root and globs into the
corpus's `meta` and the registry. What is true is the thing the contrast was always about — **no
prose an agent authors reaches the searchable text**, so there is nothing for a write policy to
govern.* The two corpora never mix in a ranking and never share the push budget.
Full spec: `design/knowledge-index.md`.

~~Four processes~~ **Five processes**: a library, a long-running service holding the warm embedder, two
thin stdlib-only clients — the MCP server and the hook — that start the service if it is absent, and a
**detached indexer** ~~the service spawns~~ **spawned** per knowledge-base build, which outlives its
caller (K8). **The service is one of two spawners**: `detach.spawn`'s callers are
`service/dispatch_knowledge.py` and `knowledge/main.py`, the second when a person starts a build from
a shell, opening the store itself and never going through RPC. Naming only the service made a
shell-started indexer with no service in the `ps` tree look impossible
(`design/architecture.md` §"Components").

```
  harness session  (kiro-cli or Claude Code)
   ├── spawn hook ──► static write policy  (+ warms the service)
   ├── user-message hook ──┐
   └── MCP tools ──────────┤
                           ▼
                  zikaron-service  (warm bge-small, open DBs)
                           │  Unix socket, JSON-RPC 2.0
                           ▼
                    zikaron-core ──┬─► .zikaron/memory.db
                           │       │     FTS5 (whole record)
                           │       │     vec0 (chunked)
                           │       └─► .zikaron/knowledge/<uuid4>.db   (one per corpus)
                           │             FTS5 + vec0 over file chunks
                           ▲       └─► detached indexer process, per build
   consolidation skill ──► subagent ──┘   (4 separate tools, memory only)

   python -m zikaron.knowledge  ─────────► detached indexer process, per build
        (a person, from a shell)             opens the store directly, no RPC
```

*(The root node read `kiro session` until 2026-09-22 — a second thing D34 left behind, unrelated to the
two-store split but in the same paragraph and equally unedited by the milestone that falsified it.)*

Both hooks fire in **subagent** sessions too, and both print nothing there: pushing retrieved gists into a
subagent's context would hand the consolidator the broad retrieval D32 withholds from it. A subagent still
reaches the service through MCP, under the **top-level** session's label. §"Subagent sessions" in
`design/architecture.md`.

## 3. Provenance of the design

`research/initial-brainstorm-transcript.md` (2026-07-31) is a Grok session in which the user surveyed the field
and stated the core design — it is the source of D1–D9. The original PDF was deleted on 2026-08-01 at the
user's request; the transcript was extracted verbatim first, so the D1–D9 rationales remain auditable against
their source. It contains a framework survey (Mem0, Letta/MemGPT,
Zep/Graphiti, "Hindsight", LangMem, A-MEM, filesystem memory, HiMem/H-MEM, MRAgent), the user's objection to
putting an extra LLM on the write path, the user's own design, Grok's analysis of how it transfers to coding
agents, and a benchmark list. **Grok's specific claims are unverified** — see `FINDINGS.md` open question 9.

The second major input is `~/Memory`, a sibling project that is a *working implementation* of this two-tier
design for a human-like character agent. Only its memory mechanisms are relevant; its own domain concerns
are out of frame. See `design/prior-art.md`.

The third input is **measurement of the harness itself**, and it arrived late enough to be instructive. Two
instruments:

| Instrument | What it settled |
|---|---|
| The embedder benchmark (`research/embedder-benchmark-results.md`, reviewed to approval over three rounds) | D20–D25, and open questions 2 and 8 |
| A **hook probe**, 2026-08-01 — a script registered on `agentSpawn` and `userPromptSubmit` for two agents, logging its stdin payload beside its own environment and `/proc` chain; five firings, raw log `/tmp/zikaron-hookprobe/log-final.jsonl`; plus direct reads of `/proc/<pid>/environ` on live kiro, hook and MCP processes | That `KIRO_SESSION_ID` is exported into every process kiro spawns and is the canonical session id, which **deleted** the `/proc`-ancestry rung of D31's label ladder and everything built to support it; and that hooks fire for subagent sessions, which **added** D32's push-suppression rule |

The second one is worth flagging as a method lesson rather than only a result. The ancestry rung had been
through **every round of independent design review the corpus had run** and was internally airtight — it had a defined race
outcome, a fail-closed ambiguity rule, a durable provenance record and an invariant policing it. What review
could not do was test whether the case it existed for occurs. One `env` check did. **Where a design rests on an
unobserved property of the environment, the corpus should say so in the same sentence** — the old text did, in
"specified but unverified", which is the only reason this was findable at all.

## 4. Settled decisions

User-stated unless noted; change only with the user.

| # | Decision | Rationale |
|---|---|---|
| D1 | **Tribal knowledge only.** ~~Codebase KB is a separate system.~~ **Amended 2026-09-15, operator sign-off: the separate system is now Zikaron's own** (`design/knowledge-index.md`, normative). The scope line governing what `remember` accepts is **unchanged** — *could you learn this by reading the code?* still excludes it from the memory store, and the two corpora never mix in a ranking or share the push budget. What changed is who supplies the other half. | Keeps the store small, and keeps memory to what cannot be re-derived from source. **The amendment is a dependency failing, not a decision reversing:** D1 delegated to kiro-cli's built-in `knowledge` and `code` tools, Claude Code ships neither, and D1's own text stayed true while the system it named stopped existing. No test, review round or harness seam can see that class of failure, because the decision remains internally consistent and only its environment moved. |
| D2 | **No extra LLM on the write path.** Hard constraint. | Cost and latency on the hot path. The primary agent already has the context and the judgment. |
| D3 | **Two tiers: journal (unconsolidated) + long-term (consolidated).** | Cheap append now, quality later, off the critical path. |
| D4 | **Memory record = `{uuid, gist, content}`.** | Progressive disclosure: gists are cheap to surface, content is fetched on demand. |
| D5 | **Read = hybrid (vector + full-text) top-K → ids + gists.** Agent may fetch full content by id, or re-search by keyword. | Exact technical tokens (error strings, env vars, command names) demand lexical matching, not just embeddings. **Clarified in review round 2:** "top-K" is two numbers, not one. Each arm retrieves to the effective config's `fusion_depth` (default **50** — the depth every quality figure in `design/retrieval.md` was measured at) and the fused list is cut to the caller's `limit` (default 5) only after penalties, ordering and the supersession repair. Collapsing them would have made the shipped pipeline a two-arm RRF over five-deep arms, which is not the pipeline that was benchmarked. **Refined in round 6, without moving the fused depth:** each arm *probes* for `fusion_depth + 1` distinct eligible memories and discards the surplus. The extra row never reaches RRF — it exists so that "the depth bound cut something" is an observed surplus rather than an inference from `depth == fusion_depth`, which was false whenever the store held exactly that many eligible memories (`design/schema.md` invariant 20). |
| D6 | **Write = primary agent's own judgment via MCP**: new journal entry / amend an existing memory (only if it was read first) / nothing. Agent authors its own gist. | Follows from D2. Re-read-before-amend guards careless overwrites — **enforced mechanically by D26**, not by trust. |
| D7 | **Consolidation is the only extra LLM**, run by a separate agent off the hot path. Code deterministically selects the long-term candidates adjacent to each journal entry; the agent decides merge vs. new. Mechanism in D29, trigger in D10. | Code picks candidates, model exercises judgment — which is also what keeps the task narrow enough that a modest model may suffice. |
| D8 | **Store scoped to the directory the harness runs in.** No global/user tier in v0. | Prevents cross-project pollution. Accepted cost: genuinely cross-project lore (toolchain preferences, org conventions) has nowhere to live. |
| D9 | **Delivered as an MCP server**, plus a distributed **skill** and **hooks**. | Harness-agnostic; retrieval and write verbs are tools, not prompt protocol. |
| D10 | **Consolidation trigger = a distributed skill the user invokes manually**, which spawns a subagent to consolidate. Migrate to a kiro-cli compaction hook or a scheduler when either ships. | `kiro-cli` exposes no compaction hook today (confirmed). Manual invocation is honest about that rather than guessing with a proxy. **Consequence: consolidation may run rarely — hence D15.** |
| D11 | **Staleness is repaired in-band by the burned agent.** Memory surfaces → agent acts on it → it does not work → agent determines the current truth → agent rewrites the memory. | Zero extra LLM, and the agent holding the fresh contradiction is the best-placed judge. Residual gap in open question 6. |
| D12 | **Read = both push and pull.** A **`userPromptSubmit`** hook injects the top **5** surfaced memories; the agent then chooses to pull full content via MCP, re-search with different keywords via MCP, or ignore them. | Push solves "the agent does not know it should ask"; pull keeps cost bounded to gists. Confirmed: exit 0 ⇒ hook stdout is added to context. **Fires once per user message, not per agent turn — see open question 1.** |
| D13 | **The gist's job is relevance triage** — enough for the agent to judge, from the injected block alone, whether this memory bears on what it is doing. | Defines the writing instruction and the eval target for gist quality. |
| D14 | **End-to-end evaluation is stoved** until an initial implementation exists. | No point tuning end-task eval against vapor; build first, measure second. **Narrowed after the corpus review:** this was written as "benchmarking is stoved", which the next eleven decisions contradict — D20–D25 are settled *from* a pre-implementation retrieval benchmark. Component measurement against a synthetic corpus is not only allowed, it is how the retrieval stack was chosen. What waits for an implementation is the measure that needs a running system and a real store: **does having memory make the agent finish the task better**. `FINDINGS.md` open question 9 tracks it. |
| D15 | **Write-time dedup, agent-resolved.** `remember` writes, then runs the same hybrid search and returns any near-duplicate above threshold in the tool result, so the primary agent can choose to amend the older record instead. Retrieval spans journal ∪ long-term. | Keeps D2 intact — no extra LLM — while making redundancy *visible at the moment it can be resolved*, which matters precisely because D10 makes consolidation rare, so the journal is the de-facto store. **Corrected after the corpus review:** this rationale used to claim dedup "stops journal duplication", which the mechanism does not do. D32 has `remember` write unconditionally and report afterwards, so the duplicate row is live either way; if the agent then amends the older record, resolving the redundancy takes a second call — `retire` the row it just created with `superseded_by` pointing at the amended one. Detection and an offered resolution, not prevention. Prevention would mean refusing a write, which D32 rejects for never-lose reasons. The instrumented signal accordingly distinguishes all four matured outcomes — fully resolved, amended-but-duplicate-left-live, duplicate-discarded-without-amend, ignored. **Round 2 gave the threshold a value; round 3 corrected where its justification comes from; round 4 corrected the justification itself.** `dedup_threshold` is a cosine floor at **0.80** on the directed score `s(new row → candidate)`, capped at `dedup_max` **3** rows. The value is a **provisional seed with no persisted measurement behind it** — round 2 quoted floor-sweep tables from a probe that scored whole-record vectors rather than the deployed first-chunk-to-best-chunk quantity and was never persisted, so those figures are withdrawn. Round 3 then replaced them with a claim that **also** exceeded the evidence: that near-miss identifier pairs "sit at absolute cosine ≈ 0.73", so no cosine floor can separate a duplicate from a twin. The approved instrument measured **query→passage** cosines — its probe is a bare identifier token or "Tell me about X." — never memory-to-memory similarity, so it locates no pair population on the axis this key thresholds; ≈0.73 is in any case bge-large-with-prefix's level (0.72–0.74), while deployed bge-small-with-prefix is 0.76–0.79; and no duplicate population was measured at all. What survives is a fact about the **signal** rather than the threshold: with topic held constant the discrimination index is **0.194–0.233**, so a near-miss identifier contributes about a fifth of the separation a plainly distinct token does, direction right in 14/14 blocks with a thin margin. A `WidgetV1`/`WidgetV2` pair is therefore exactly where the dense score is weakest, and **nothing in the corpus says which way moving this floor trades duplicates against twins.** So a floor cannot be *asserted* to separate them, the hand-back is **candidates for the agent to compare, never an assertion of duplication**, and the tool description says so. Reasoning, the withdrawal and the round-4 narrowing: `design/consolidation.md` §"Where the three cosine seeds come from" and §"Why not cosine alone". |
| D16 | **Soft delete only** — retire (`active=0`), row + FTS + vec retained, recoverable. Never hard `DELETE`. | `~/Memory`'s amnesia guard: one bad session must not be able to destroy accumulated lore. Retire requires a prior read on the same terms as amend, enforced by D26. **Clarified in review round 3:** "never hard `DELETE`" constrains the **agent-facing API** — no tool, RPC method or internal code path deletes a memory row. It is not a claim that the bytes are unremovable, and reading it that way made the corpus's own secret-erasure guidance both wrong and self-contradictory. An operator holding the 0600 SQLite file is outside that boundary by construction, the same boundary `design/architecture.md` §"Filesystem security" draws for the file itself; the exact erasure transaction, and what it still fails to erase, is `design/write-policy.md` §"Inspection, deletion". The decision is unchanged: no agent gets a hard delete. |
| D17 | **Scope key = the harness's own project directory where it names one, else the current working directory.** No VCS-root walk, no marker file. | **Amended 2026-08-18, on the revisit condition this row itself named.** Original text: *"Scope key = literally the current working directory"*, deferred pending "monorepo / subpackage / worktree pain in practice" — which arrived, in a form nobody predicted. Claude Code persists the working directory across shell calls, so an agent's own `cd` moved the value the hook keys on while `zikaron-mcp`, spawned once at session start, stayed put: **push and pull silently answered from different stores.** Measured on live sessions — 39 cwd transitions in one, a store created under a log directory, and 20 pushes over two hours returning nothing while the same session's MCP tools kept working. The literal-cwd rule was never wrong so much as **implemented twice**; the amendment is one resolver (`HarnessSpec.store_scope_dir`) that both clients call, reading `CLAUDE_PROJECT_DIR` under Claude Code and falling back to cwd where a harness names nothing. **Kiro's fallback is its unchanged behaviour, not a degraded mode** — it exports no such variable and restores the working directory rather than persisting it, so it never had the defect. That last clause rests on an operator observation and twelve days of stray-free history, and is **not measured**; `tests/test_harness_store_scope.py` names the dependency at the point where it would have to change. |
| D18 | **Memory instructions and write policy are injected by an `agentSpawn` hook.** | Fires once at session start, and its stdout also reaches context. So the instruction block is stable for the whole session, sits early, and does not churn the prompt cache the way per-message injection does. Clean split: stable prose in `agentSpawn`, churning gists in `userPromptSubmit`. |

Memories live only in the local SQLite DB — never committed to git.** | Proven in `~/Memory`, and the MCP server is Python anyway. Store artifacts are local state, not team artifacts. `.gitignore` updated accordingly. **Configuration is TOML, not database rows — see D33.** |
| D20 | **Keep `bge-small-en-v1.5`, and pass the documented BGE query prefix** on both paths. Record embedding model id + dimension per vector; force full reindex on any change. | Benchmarked. `bge-large` showed **no demonstrated task gain in the deployed hybrid** at 13× embed latency / 20× disk / 4.1× cold start. Prefix costs 1.19 ms and gains +0.026 useful-recall dense-only (CI excludes 0). *Not* "bge-large is worse" and *not* "scale is disproved" — see open question 8. |
| D21 | **Embed gist + content, not gist alone.** | Gist-only costs −0.026 to −0.130 useful-recall@5 across all eight dense-bearing configs on the blind set. Truncation handling stays open (open question 3). |
| D22 | **The `userPromptSubmit` hook must never load an embedding model, and never reads the store itself.** It talks to the already-warm service; on any RPC failure it logs the failure to `hook.log` and relays it to the model via stdout, never falling back to a direct store read. | Measured: cold whole-process bge-small = **783 ms**, versus 0.26 ms warm for BM25-only. 0.8 s of dead time on every user message is unacceptable on the critical path — the decision that no model runs in the hook, ever, is unchanged. **An earlier draft had the hook fall back to a direct BM25-only read of the store on a transport failure, exempting `bad_config` and `reindexing` as store-level problems a direct read cannot safely route around.** That exemption was itself evidence the fallback was wrong in kind: a mechanism that has to special-case away the cases where it would be most dangerous is a bypass wearing a resilience mechanism's name. **Superseded 2026-08-01: on every failure, transport or store alike, the hook appends one line to its own `hook.log`.** Its own file, not shared with the service (`service.log`) or the `agentSpawn` warm helper (`warmup.log`) — three independent processes writing one path through `logging.FileHandler` would be a real cross-process append race, so each gets its own. And the write is a direct `open`/`write`, not `import logging`: measured at ~15 ms of interpreter cost on this machine, which is the same class of number that justifies keeping this client stdlib-thin in the first place, so the service and the warm helper use `logging` (off the critical path) while the hook does not. **Revised again 2026-08-03, after a live spike measured the intervening stderr/non-zero-exit revision wrong**: the hook now exits 0 unconditionally and, on failure, also prints a short, model-facing relay instruction to stdout — the one channel the spike confirmed actually reaches the model on this build — asking it to tell the operator, with `hook.log` named as the source of the exact detail. No fallback query, no re-validation, no direct reader. Full mechanism: `design/architecture.md` §"Degraded modes"; `design/coding-standards.md` §6. |
| D23 | **No cross-encoder reranker on the push path.** Left open for the pull path. | Full curve measured (5/10/25/50 candidates × gist-only/gist+content): exactly one point fits a 200 ms budget — gist-only at 5 candidates, 184 ms — and reranking 5 candidates is operationally pointless. Pull path is viable at 1908 ms for 50 gist-only pairs, since a deliberate search can afford it. |
| D24 | **Reject the extracted-identifier `tokens` column as specified.** | Own proposal, killed by its own evidence. Factorial ablation: the `tokenchars` tokenizer alone **costs** −0.052 useful-recall; the tokens field only recovers +0.037; duplicate emission does nothing; net −0.016 against the true baseline. The frozen extractor then failed held-out — recall 0.42 (gate 0.70), precision **0.36 strict / 0.54 lenient** (gate 0.80), spurious tokens on 6/7 numeric-prose sentences, scoped-npm recall 0.125, git-hash recall 0.125. *Narrow escape hatch:* custom tokenization confined to the extracted field alone is **untested** — FTS5 cannot give one table two tokenizers. |
| D25 | **Supersession is structural, via `superseded_by` — and it demotes rather than hides.** | Measured, at the scope the report actually gives it: on the **6 current-action polarity stubs (18 prompts)** a superseded record lands in the injected five **83–100%** of the time and outranks its own correction **28–50%**. n=6 stubs, too few for a rate to two decimals. Ranking cannot fix this. But blanket suppression is rejected: it would take the **4 historical-intent stubs (12 prompts — the report calls this cell indicative only)** from 0.75 to **0** — "why did we pin to 2.3.1 back then" needs the retired record. **Mechanically, "demote rather than hide" is a query-predicate decision**, and the corpus review caught the specs contradicting it: a default `active = 1` filter hides every superseded row. The predicate that implements it — live ∪ superseded by default, outright-retired only on request — is `design/schema.md` §"Retrieval eligibility"; the two demotion penalties, the ordering rule and the surfaced label are `design/retrieval.md` §"Supersession: eligible, demoted, and labelled". **Corrected in review round 2:** the ordering rule was written as "the replacement is placed immediately above the record it replaced", which is unsatisfiable — a `merge` absorbing two rows into one gives them a shared replacement, and no linear order puts it immediately above both. The realizable rule is **precedence**: every retrieved replacement outranks every record it replaced, by a stable topological pass over the fused pool before the cut. **Round 3 added the case where a lineage dies:** an ordinary `retire` of a replacement is legal and produces a *terminal component* — a chain whose head is itself retired outright, meaning "no longer true, and nothing replaces it". Eligibility deliberately does not chase the chain to find that out, because resolving root state per candidate would put a graph walk in the ranking path; the surfaced block names the immediate replacement and `fetch` reports whether that head is still live (`superseded_by_latest_state`). Cheap ranking, full truth on the pull. |
| D26 | **Optimistic concurrency on every mutation.** Each memory carries a monotonic integer `version`, bumped on every write. `amend` and `retire` require the caller to pass the version it read; a mismatch **rejects** the write and returns the current record — gist, content, and new version — in the failure payload, so the agent re-decides in one round trip. Applies to journal rows and long-term records alike, and to the consolidator, which is the likeliest racer. | A genuine lost-update guard: two kiro sessions in one directory share the store. A conflict is *informative*, not merely an obstacle — it often means another agent already repaired the staleness this one is trying to fix, which is exactly what the payload lets it see. `~/Memory` already carries a `revision` counter as an informational drift watch; this makes it load-bearing. **Corrected after the corpus review — how D6's read-before-amend is actually enforced.** The original rationale claimed "the agent cannot produce a valid version without having fetched the record". That is false as specified: `version` starts at 1 and increments, `remember` and `amend` return it, so an agent holding a uuid from a search result or an injected gist can simply guess `1`. A predictable integer prevents lost updates; it does not prove a read. The enforcement is therefore explicit: the store keeps a **read receipt** per `(session_id, client_kind, uuid, version)`, minted only when full content was actually delivered — by `fetch`, by a consolidation group payload, by a conflict response, or by the caller's own successful write — and every mutation requires a matching receipt for every row it touches (`design/schema.md` invariant 9). **`client_kind` was added to that key on 2026-08-01**, when the empirical `KIRO_SESSION_ID` finding (D31) made every client of one kiro session share a `session_id`: on the old key a receipt minted by the consolidator's `next_group` serve would have licensed the *primary* agent to amend that row without ever fetching it, decaying read-before-amend from *this agent read it* to *some client of this session did*. Lost-update protection never depended on the receipt, so only the informed-write half was at risk — and it was a latent hole, not a new one, since an `ancestry`-derived consolidator label pooled identically. **Corrected again in review round 2, twice.** (1) The precise claim is *"`fetch` is the only way to license a write to a pre-existing row, absent an own-write or conflict response for that row in this session"* — the looser "`fetch` is the only source of a version" was falsified by `remember`/`amend` returning versions and by the conflict payload. (2) **The version check must run before the receipt check**, because a version bump revokes receipts: checking receipts first would report `no_read_receipt` for every ordinary lost-update race and turn the promised one-round-trip retry into two. The full precedence ladder is `design/architecture.md` §"Validation precedence" — **two** ladders as of round 3, because for the four consolidator verbs group authorization has to run ahead of version, or a conflict payload becomes a read primitive (see D32). **Limit, stated plainly:** this enforces read-before-write, not understood-before-write — it is a concurrency and provenance guard, never a quality guard. |
