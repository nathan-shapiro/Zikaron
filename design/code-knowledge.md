## 1. What is proposed

Agents that **populate** a knowledge base, rather than only search one: a corpus of per-source-file
documentation, generated by a crew of subagents, indexed as an ordinary knowledge base, and read
by agents to find where to start before they grep. Two halves:

- **The producer** generates the documentation. Invoked for a module (a directory of the
  repository), it writes `code-knowledge/<module>/<path>/<file>.<ext>.md` for each source file
  `<module>/<path>/<file>.<ext>`, plus a module `README.md`, and on later runs regenerates only what
  the source has moved under.
- **The consumer** is the agent using it, and what it is told and shown about what to trust. Each
  search result from a generated document says whether the source it describes has changed since
  it was documented.

**The motivating evidence is the operator's, and it is not measured here**: the same pattern,
used on a codebase of ~10M lines where agents could not find where to start on a feature, under
kiro's `knowledge` tool, with the consuming agent told to check staleness itself against the hash
each document carries. Zikaron owns its knowledge tool, so the check can move into the tool's
response — which is what K14 is.

**Neither repository this project dogfoods in can show the benefit.** `zikaron/` is 200 source
files and LeibaTrader 243, sizes at which grep still finds things. They exercise the plumbing only.

## 2. Proposed decisions

### D39 — code knowledge: a producer and a consumer

- **The documents are files in the project**, indexed as an ordinary knowledge base. The index
  stays authorless: it indexes files and does not know who wrote them. The producer sits outside
  both stores, as the guards do (D38).
- **It amends D7**, which says consolidation is the only extra LLM. The producer is a second, and
  like the first it is invoked explicitly and sits on no critical path. D2, which governs the memory
  store's write path, is untouched.
- **Code plans, the model writes** — D7's pattern. Which documents are missing, stale or orphaned is
  a deterministic comparison of hashes; a model is needed only to write a file's document and the
  module README.
- **Dependencies are forward edges only**, with no transitive closure. A file's own imports are in
  the file, so its hash covers them. What depends on a file is not, so it is never written down;
  searching the corpus for the file's path finds every document that lists it.
- **The consumer trusts but verifies.** A document whose source has changed is a lead, not a fact:
  it still says where to look, and its specific claims are checked against the source.

### K14 — linked knowledge

**Specified, with its rejected alternatives, in `design/knowledge-index.md` §7.7, §7.7.1 and §15**,
and built by `design/build-plan.md` §M39. A document's front matter names its source and that
source's hash, and every search result from it says whether the source has changed since.

### Rejected alternatives

- **A model orchestrating the plan.** What changed is a comparison of hashes.
- **Model-written reverse dependencies.** They go stale when another file changes, and the
  documented file's hash cannot see it.

## 3. Proposed milestones

**M39 first, then M40**: M39 fixes the contract M40 writes to, and stands on its own for any corpus
derived file by file from another.

### M39 — linked knowledge

**Briefed**: `design/build-plan.md` §M39. What its brainstorm settled with the operator is recorded
in the spec it builds against, each choice marked with the operator and the date.

### M40 — the producer

A deterministic planner command that reuses the indexer's discovery (`design/knowledge-index.md`
§4.1, so the producer and the index agree on what a file is) and lists documents missing, stale and
orphaned; the generator skill; the documenter agent; the document format — front matter carrying
K14's two keys, beside the generator prompt's digest and the model under keys of the producer's own,
and sections for purpose, non-trivial symbols, what is not obvious, and forward dependencies; the
module README; the consumer's steering text; all installed for both harnesses the way the
consolidation skill is. **It hashes through K14's one function**, so what it records is what search
compares against.

**To settle in its brainstorm:**
- **whether a Claude Code subagent can spawn subagents** — unverified here; making the skill's own
  session the orchestrator does not depend on it. kiro's subagent support likewise;
- where *search before you grep* is said: the corpus description, the tool description, or a
  session-start text injected only where a code-knowledge corpus exists — unprompted recall is bursty,
  at 6–11% of turns (`FINDINGS.md` Q16);
- whether the documents are committed — the default `git_mode`, `tracked`, hides uncommitted ones,
  so the producer registers its corpus with `all` unless that default changes first;
- regeneration cadence and cost. Measured on `zikaron/`: regenerating every touched file at every
  commit would have cost about 2.5× the first build over 60 days. Tokens per document are unmeasured.
  Git's index and its own modified-file detection can find what changed across a whole corpus
  without reading every source (`research/code-knowledge-sizing.md` §1);
- scale: the largest corpora measured are 2,720 chunks for retrieval quality (M25) and 2,033 files
  for a scan without embedding (`research/m21-scan-throughput.md`); the ~22,800-chunk mid-size
  figure `design/knowledge-index.md` uses is an estimate, and search latency at scale is unmeasured.
  A ~10M-line codebase is on the order of 10⁵ files at ~100 lines each, and dense search scans every
  chunk — which argues for one corpus per module;
- **evaluation**: localization — the right files for a feature, and the tokens spent reaching them —
  grep alone against code knowledge, on a large repository the model has not memorized, screened by
  M26's first-tool-call test. A prior-art and localization-benchmark brief to memory-assistant is
  owed before this brainstorm;
- **the CTIM-Rover risk** (`design/evaluation.md` §"The negative result is the important one"):
  agent-written code knowledge measurably hurt. This differs — file fragments, per-file provenance,
  a staleness state in every result — but gives up being only agent-*read*, one of the three
  differences that section rests on.
