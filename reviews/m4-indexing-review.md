## Round 1 — 2026-08-01

**Summary judgment:** The normal M4 path is thoughtfully structured and closely matches the design: preflight and embedding precede `BEGIN`, indexed writes compose the M3 neutral cores, FTS replacement uses the pre-write document, vector deletion order is correct, and the four build-plan done-when cases have substantive tests. It is not ready to ship because one defensive chunking path can return an invalid but plausible plan, and the transaction wrapper makes the architecture's `store_busy` contract impossible to honor. Dependency pins, typing structure, SQL parameterization, and the no-retrieval scope fence otherwise look sound.

**Findings:**

1. **[BLOCKER] A count/span disagreement silently returns a chunk over its own effective budget.** `zikaron/core/indexing/chunking.py:139-150` treats an empty span list as `(paragraph,)`, after `_pack` has already established that the paragraph exceeds `budget`; no later check asserts `chunk.token_count <= effective_budget`. `tests/test_indexing_chunking.py:test_an_encoder_whose_count_and_spans_disagree_loses_no_text` currently blesses the resulting contradiction: the returned chunk has `token_count == 999` under `effective_budget == 3`. The assembled-cap assertion does not repair this when the model cap is larger than the configured chunk budget, so the preflight returns a healthy-looking plan that violates step 5 and the test suite's own budget property. Reject inconsistent span data instead of returning a plan: validate one ordered, non-overlapping span per counted token (the runtime implementation in `zikaron/core/indexing/encoder.py:227-235` currently checks only range), and assert freshly counted emitted pieces do not exceed `budget`. Use the existing `assembly` stage if this is detected during preflight (and broaden that stage's design wording accordingly), or report `bad_config` while loading/validating the artifact; add tests for empty, overlapping/out-of-order, and count-mismatched spans that assert no plan is returned.

2. **[BLOCKER] SQLite lock contention is converted to the wrong wire error, while transaction-boundary failures escape raw.** `zikaron/core/indexing/writes.py:_in_one_transaction` catches every `aiosqlite.Error` raised by `work` and converts it to `index_failed(index_write)`. A `SQLITE_BUSY` after the configured timeout must instead be `store_busy {verb}` under `design/architecture.md` §Errors; once this wrapper has erased the SQLite error, M9 cannot correct it. Conversely, `BEGIN` is outside the `try` and `commit_or_roll_back` runs in `finally`, so failures at transaction start or commit escape as raw driver exceptions despite `remember`/`amend` promising domain errors. Pass the verb into the wrapper, cover begin/work/finalization with one exception-mapping policy, map SQLite busy/locked contention to `STORE_BUSY` and other write failures to `INDEX_FAILED/INDEX_WRITE`, and leave the connection rolled back when SQLite leaves a transaction active. Add focused tests for timeout contention and injected commit failure, including the returned code and absence of partial indexed state.

3. **[IMPROVEMENT] The invariant-1 write test cannot detect vectors attached to the wrong chunk.** `tests/test_indexing_writes.py:test_remember_writes_one_chunk_and_one_vector_per_part` checks only that the set of `memory_vec.rowid` values equals the set of chunk ids. Reversing the prepared vector sequence before the `zip` in `zikaron/core/indexing/vectors.py:insert_chunks` would preserve every asserted rowid and all current multi-chunk determinism checks while silently making each embedding describe another `part_index`. Extend that multi-chunk test to read each vector through its joined `chunk_id` and compare it with the normalized `vector_for(plan.chunks[part_index].embedded_text(gist), dim)`; this directly mutation-tests the semantic pairing invariant rather than only its integer keys.

4. **[IMPROVEMENT] Production docstrings contain circumstantial milestone/history provenance forbidden by the coding standard.** Examples include `zikaron/core/indexing/__init__.py` (the contract was “left to be inferred” and is “now written”), `zikaron/core/indexing/writes.py:29-31` (“the milestone above” / “write-path milestone”), and repeated M3/M4/M6/M7 ownership references in `zikaron/core/records/memory.py` (notably lines 1-11, 285, 333-348, 473-476, 684-695, and 778). These descriptions will become stale when the build plan is complete and obscure the timeless ownership boundary. Rewrite them in terms of current components—row primitives, indexed composer, tool-facing write layer, and consolidation layer—and retain only the load-bearing reasons (transaction ownership, tokenizer/index dependency, and event field ownership).

VERDICT: NEEDS_CHANGES

## Round 2 — 2026-08-01

**Summary judgment:** The ordinary indexing path remains strong, and the Round 1 vector-pairing and provenance remediations are correct; the `remember`/`amend` event payloads also match the fixed per-kind shapes, the M4 boundary enforces the applicable prose bounds, and the broadened `assembly` description honestly covers both emitted-chunk and assembled-sequence checks. It is still not ready to ship because the count/span remediation has a passing content-loss counterexample, and transaction finalization can leave an uncommitted write live after reporting failure; the contention mapper also misses a reachable SQLite extended result.

**Findings:**

1. **[BLOCKER] A partial but well-ordered span list still loses content and passes the new plan post-condition.** `zikaron/core/indexing/chunking.py:127-150` (`_hard_split`) trusts however many spans an `Encoder` returns, while `zikaron/core/indexing/chunking.py:262-286` (`_assert_plan_is_within_its_budgets`) checks only the token count of the pieces that were emitted. For a paragraph of eight whitespace tokens at budget 2, an otherwise substitutable encoder can count 8 but return valid, ordered, non-overlapping spans for only the first four tokens; `_hard_split` emits two 2-token chunks, silently omits the remaining four tokens from the dense index, and both budget/cap checks pass. This directly disproves the Round 1 rationale that the plan post-condition catches count/span disagreement from a foreign `Encoder`; the two new tests cover zero spans and spans that are too coarse, but not incomplete spans. In `_hard_split`, compare `len(spans)` with a fresh `count_tokens(paragraph)` and reject at `assembly` when they differ (the extra count is needed only for an already-oversized paragraph, not for every token count); also reject zero-width token spans or otherwise state and enforce their safe semantics. Add a regression encoder that returns only a valid prefix of the expected spans and assert that no plan is returned.

2. **[BLOCKER] A failed commit is mapped but not cleaned up, leaving the supposedly failed mutation live on the connection.** `zikaron/core/indexing/writes.py:339-352` (`_finalize`) converts an exception from `commit_or_roll_back` and immediately raises, without rolling back if SQLite left the transaction active. `tests/test_indexing_writes.py:550-574` masks this by explicitly calling `store.connection.rollback()` in the test's `finally`; therefore the test proves only the wire code, not the Round 1 requirement that finalization leave the connection clean. After a real failed `COMMIT`, the staged memory/index/event rows can remain visible on that connection, the next call's `BEGIN` can fail as a nested transaction, and a later accidental commit can durably publish a write already reported as failed. On finalization failure, attempt rollback whenever the connection remains in a transaction; if rollback itself cannot restore a clean state, invalidate/close the connection rather than returning it to the pool. Change the test to require `not connection.in_transaction`, verify no state through a second connection, and prove a subsequent write can start normally without test-side cleanup.

3. **[BLOCKER] Exact-name matching misclassifies extended busy/locked results as terminal index failures.** `zikaron/core/indexing/writes.py:321-336` recognizes only the strings `SQLITE_BUSY` and `SQLITE_LOCKED`. Python exposes extended results through `sqlite_errorname`, so `SQLITE_BUSY_SNAPSHOT` and `SQLITE_LOCKED_SHAREDCACHE` miss the set and become `index_failed(index_write)`. `SQLITE_BUSY_SNAPSHOT` is reachable on the deferred `amend` transaction: it reads the row/receipt, another WAL connection commits, and its later update cannot promote the stale snapshot; retrying the whole call is exactly what allows the documented `version_conflict` to be observed, but the current terminal answer suppresses that retry. Classify by the primary result code (for example, `sqlite_errorcode & 0xff` against SQLite's `BUSY`/`LOCKED` constants), add an injected extended-code test and preferably a real two-connection WAL snapshot race, and broaden the `store_busy` wording from only “past busy_timeout” to include retryable snapshot/lock contention.

4. **[IMPROVEMENT] The main write suite is labelled unit while exercising real sqlite-vec.** `tests/test_indexing_writes.py:1-6` explicitly calls itself the “Unit tier” but uses `Store.create` and a real `memory_vec` virtual table throughout. `design/coding-standards.md` §4 assigns real sqlite-vec tests to `@pytest.mark.integration`; leaving this unmarked makes marker-based tier selection misleading even though the default check currently runs both tiers. Add module-level `pytestmark = pytest.mark.integration` (the fake encoder can remain), or replace the extension behind a genuinely hermetic unit boundary and keep only the real-store cases marked integration.

VERDICT: NEEDS_CHANGES

## Round 3 — 2026-08-01

**Summary judgment:** The span/count remediation is correct for empty and short span lists, the retokenization-drift test reaches the intended emitted-chunk post-condition, and primary-result-code classification correctly handles both injected and real `SQLITE_BUSY_SNAPSHOT`. Keeping hermetic `tmp_path` stores in the default tier is also the right policy; marking this suite `integration` would buy no useful isolation from external or model-loading work. The implementation is still unsafe on the second failure in commit cleanup: if the compensating rollback fails, `_finalize` suppresses that fact and returns the borrowed connection to its owner in potentially transaction-active state.

I could not independently execute `./check.sh` because this reviewer session exposes no process-execution tool; I inspected the current implementation, tests, and named normative sections directly.

**Findings:**

1. **[BLOCKER] A failed rollback after a failed commit can still return a live, dirty connection.** `zikaron/core/indexing/writes.py:339-377` (`_finalize`) correctly attempts rollback after `commit_or_roll_back` fails, but `contextlib.suppress(aiosqlite.Error)` discards a failure of that cleanup and then leaves the same connection in circulation. In that reachable double-failure case, the staged memory/index/event rows may remain visible and later commit even though the call returned `index_failed`; this contradicts the function's “leaving the connection out of a transaction either way” contract, `INDEX_FAILED`'s “transaction rolled back” wire message, and invariant 2. Borrowing the connection does not make it safe to return after its transaction state could not be repaired; disrupting other users of a poisoned connection is safer than allowing a reported-failed mutation to publish later. The smallest fix is to close/invalidate the connection when the compensating rollback raises (then raise the already-mapped failure), and add one test that injects both commit and rollback failure and proves a second connection sees no rows and the failed connection cannot be reused (or has been replaced by its owner).

2. **[IMPROVEMENT] The stable `store_busy` message still falsely says every case exhausted `busy_timeout`.** `zikaron/core/errors.py:218-221`, `zikaron/core/indexing/writes.py:423`, and `tests/test_error_codes.py:220` retain “the store stayed locked past the busy timeout,” but the newly and correctly handled `SQLITE_BUSY_SNAPSHOT` path is normally immediate and does not run the busy handler. `design/architecture.md:1181` now states the broader contract accurately. Change the stable message and write docstring to wording such as “retryable store contention prevented the write,” and update the exact-message test.

3. **[NITPICK] The tier table still lists real sqlite-vec as integration despite the explicit exception immediately below it.** `design/coding-standards.md:67` names “real sqlite-vec” in the integration row, while lines 69-77 correctly place a real sqlite-vec-backed store on `tmp_path` in the default tier. The no-marker decision is sound; simply remove “real sqlite-vec” from the integration row (or qualify it there) so the summary table and operative rule do not point in opposite directions.

VERDICT: NEEDS_CHANGES
