## Round 1 — 2026-08-01

### Summary judgment
The row mechanics are generally clear and strongly typed: retirement remains soft, retired and superseded states stay distinct, chain resolution is bounded, receipt keys are correctly scoped, and no chunk/FTS/vector writes cross the M3 fence. It is not ready to ship, however, because the retire ladder misorders target existence, single-row conflicts use the wrong wrapper shape, the transaction-owning API cannot support the atomic M4/M6 composition it promises, and two required invariant tests do not actually exercise the properties they name.

### Findings
1. **[BLOCKER] `retire` checks the replacement target's existence after source version and receipt, violating the fixed primary-agent ladder.** `design/architecture.md:1085-1092` requires existence of *every named uuid* before version and receipt, and the error table explicitly includes an unknown `superseded_by` target under `not_found`. Instead, `zikaron/core/records/memory.py:590-593` authorizes the source through existence/version/receipt first and only then calls `validate_new_edge`; target loading and `NOT_FOUND` occur inside that later helper at `zikaron/core/records/supersession.py:125-127`. Thus a stale source plus an unknown target returns and durably logs `version_conflict`, and a current unreceipted source plus an unknown target returns/logs `no_read_receipt`, when both calls must stop at target `not_found`. Split target existence from supersession state legality: load every named uuid before `_authorize_mutation` advances to version, then pass the loaded target into a legality-only edge validator (or otherwise avoid a second drifting lookup). Add precedence tests combining an unknown target with (a) a stale source version and (b) a missing source receipt; both must raise `NOT_FOUND` for the target and commit no event or receipt.

2. **[BLOCKER] Single-row version conflicts put `current` in a list, contrary to the one-object `CONFLICT_RECORD` contract.** `design/architecture.md:710-716` says `amend` and `retire` return one object for single-row verbs and reserves lists for multi-row consolidator verbs. `zikaron/core/records/memory.py:421` raises with `current=[record]`, and `tests/test_records_memory.py:779-780` bakes that mismatch in by casting and unpacking a list. Change the single-row error payload to `current=record` and update the test to assert that `data["current"]` is exactly one `ConflictRecord` with the documented fields; future multi-row verbs should continue to use lists.

3. **[BLOCKER] The transaction-owning row API cannot be composed into the atomic M4/M6 operations it claims to support.** The package promises that M4 wraps `create`/`amend` with indexing and the event in the same transaction (`zikaron/core/records/__init__.py:13-14`), while schema invariant 2 requires one transaction over prose, indexes, receipts, and events (`design/schema.md:924-929`). But `create` opens and commits its own transaction (`zikaron/core/records/memory.py:296-308`), as do `amend` (`:545-559`) and `retire` (`:588-618`); calling them under an outer transaction will fail at `BEGIN`, while calling them first exposes committed prose before M4's index/event work. This also leaves no atomic place for M6 to satisfy `remember`'s required new-row `own_write` receipt (`design/architecture.md:687`), which `create` explicitly omits (`memory.py:286-289`). Refactor into transaction-neutral row operations plus transaction-owning standalone wrappers (or a single explicit unit-of-work owner); M4/M6 must invoke the neutral operations and commit exactly once after index, receipt, and event work. Add a composition test that performs a row operation plus a sentinel downstream write, injects a failure before the outer commit, and proves neither write survives.

4. **[BLOCKER] The invariant-10 tests show co-occurrence after a call, not atomicity, so they would pass if mutation, receipt, and event were committed in separate transactions.** The retire test only checks that an event exists after success (`tests/test_records_memory.py:893-908`); the fetch, conflict, and no-receipt tests likewise inspect final state (`:882-888`, `:913-948`, `:953-970`). None creates a failure between the coupled writes, despite `design/coding-standards.md:69-74` requiring an invariant test that fails when the invariant is violated. Add deterministic failure-injection tests: make `_log_event` raise after retire's row/receipt changes and assert row, version, receipt set, and event log all remain at their pre-call state; make it raise after fetch/conflict receipt minting and assert no receipt or event survives. Also assert exact event cardinality and detail, not merely `"retire" in kinds`. Keep the existing successful rejection tests to prove the deliberate commit-before-raise carve-out.

5. **[BLOCKER] The test named for the concurrent cycle-closing acceptance case is explicitly sequential.** Schema invariant 6 names “two concurrent attempts to close a cycle” as an acceptance test (`design/schema.md:988`), but `tests/test_records_memory.py:386-419` says it sequences two already-obviously-cyclic retries on one connection. That test cannot expose a check-then-write race in which `A→B` and `B→A` both validate against the same initial snapshot. Open two connections to the same store, mint each caller's receipt, synchronize the two calls after edge validation, and race opposite edges; assert that at most one commits, the other is rejected or safely retriable after SQLite contention, and a final graph walk remains acyclic. This should exercise the real transaction/locking behavior rather than merely run the ordinary cycle branch twice.

6. **[IMPROVEMENT] `CallContext` is partly a PLR0913 workaround rather than one cohesive domain value.** Its own explanation admits that `max_depth` is not call identity and is grouped “anyway” because argument count rose (`zikaron/core/records/memory.py:38-50`). In contrast, `ReceiptKey` is exactly a persisted composite key and `Rewrite` is an actual paired payload, so those two bundlings are genuine. Keep `CallContext` to request/audit identity (`session_id`, `client_kind`, `op_id`) and put `supersession_max_depth` in a small records/supersession policy value passed separately; this preserves the lint bound without making configuration masquerade as caller context.

7. **[NITPICK] Two comments retain circumstantial provenance forbidden by the binding standards.** `zikaron/core/records/receipts.py:4-5` cites a dated “finding,” and `tests/test_records_memory.py:206-207` cites a prior “review BLOCKER”; `design/coding-standards.md:93-108` requires the timeless reason instead. Rewrite them as direct rationale (shared session labels require `client_kind` isolation; inactive does not imply a replacement) without the date/review history.

VERDICT: NEEDS_CHANGES

## Round 2 — 2026-08-01

### Summary judgment
The existence-rung ordering and single-object conflict payload are now correct, the failure-injection tests genuinely exercise rollback boundaries, `CallParams` is an acceptable resolution of the prior improvement, and the cited circumstantial-provenance comments are gone. The milestone is still not ready to ship: rejection paths can commit unrelated writes from a composing caller, and the purported concurrent cycle test races two identical already-illegal calls rather than opposite edges. The corrected target-precedence behavior also lacks the requested invariant regression tests.

### Findings
1. **[BLOCKER] The transaction-neutral mutation cores can still commit arbitrary earlier writes owned by their composing caller.** `_reject_version_conflict` and `_reject_no_receipt` call `db.commit()` directly (`zikaron/core/records/memory.py:461,483`), and `_amend_within_transaction`/`_retire_within_transaction` reach those helpers (`memory.py:581-598,649-665`) despite being advertised as transaction-neutral. The validation ladder orders this verb's own authorization before this verb's mutation; it cannot prevent an outer M4/M6 caller from executing a sentinel/index write before invoking the core. In that case a stale-version or no-receipt rejection commits the sentinel too, and the caller's subsequent rollback is a no-op. The new composition rejection test avoids the hole by deliberately writing nothing before the call (`tests/test_records_memory.py:1293-1329`), so it proves only the safe special case. Move rejection commit policy to the transaction-owning orchestration layer: neutral cores must never commit or roll back, while an owner that structurally guarantees authorization is first may commit the staged audit rejection. Alternatively provide a unit-of-work API that enforces that ordering. Add a regression test that writes a sentinel before a rejected neutral-core call and proves the sentinel is not accidentally committed along with the receipt/event.

2. **[BLOCKER] The concurrent cycle acceptance test still does not exercise the check-then-write race named by invariant 6.** The setup first commits `A→B` (`tests/test_records_memory.py:407-415`), then both connections submit the same `B→A` call (`:426-449`). Each validator can therefore see the already-existing edge and reject `B→A` as a cycle without either racer attempting a write; `asyncio.gather` and two real connections do not make those duplicate, already-illegal reads the intended race. The permissive `len(successes) <= 1` assertion (`:454-464`) consequently passes when both calls return `BAD_SUPERSESSION`, which is the ordinary outcome and says nothing about simultaneous `A→B`/`B→A` validation against an initially edgeless pair. Start with both rows live, mint the appropriate receipts, run `A→B` on one connection and `B→A` on the other, and synchronize both after edge validation but before their updates so both observe the same initial graph. Then require that no more than one edge commits (allowing the loser to report a documented legality or SQLite-contention outcome) and walk both final rows, or query the graph directly, to prove no cycle survived.

3. **[BLOCKER] The corrected unknown-target precedence has no end-to-end regression test.** The implementation now does the right thing: `_authorize_mutation` loads the subject and every additional named uuid before checking the subject's version or receipt (`zikaron/core/records/memory.py:514-529`), and `retire` supplies `(uuid, superseded_by)` (`:662-665`). However, `tests/test_records_memory.py` has no case combining an unknown `superseded_by` with either a stale source version or a missing source receipt; the only unknown-target test calls `supersession.validate_new_edge` directly (`tests/test_records_supersession.py:69-80`), bypassing the ladder entirely. Add both previously requested `retire` precedence cases and assert `NOT_FOUND` names the target and that neither a conflict/no-receipt receipt nor an event is committed. These tests are required to make the observable ladder invariant fail if this exact ordering regresses.

4. **[IMPROVEMENT] The new atomicity injections are sound, but the successful retire event assertion still does not verify exact cardinality or detail.** The retire injection confirms its row update ran, the injected failure fired, and active/version/receipts/events returned to their prior state (`tests/test_records_memory.py:1343-1403`); the fetch injection likewise necessarily fires at the event insert and proves neither receipt nor event survives (`:1407-1438`). But the ordinary success test still only asserts `"retire" in kinds` (`:994-1011`), so duplicate events or incorrect `from_version`, `to_version`, or `superseded_by` detail would pass. Query the retire event rows and assert exactly one row with the complete expected JSON detail; tighten the rollback test's event assertion to the exact pre-call list as well.

VERDICT: NEEDS_CHANGES

## Round 3 — 2026-08-01

### Summary judgment
All four runtime fixes are substantively correct: the neutral rejection helpers no longer end transactions, `_commit_or_roll_back` correctly reserves commits for success and the two carve-out `ZikaronError` codes, a bare outer rollback protects a previously staged sentinel, and the concurrent test now barriers two legal opposite edges after both real validations. The new end-to-end precedence cases exercise `retire`, while the exact retire-detail and rollback assertions are stronger as requested. Two material test/documentation inconsistencies remain, so the milestone is close but not yet ready to ship.

### Findings
1. **[IMPROVEMENT] Core docstrings and a regression test still describe the removed commit-inside-rejection mechanism.** `_reject_version_conflict` opens by saying it will “commit, raise” and says “This function's own commit is what makes that true” (`zikaron/core/records/memory.py:450-457`), before contradicting itself with the correct “Does **not** commit” contract at `:466`; `_amend_within_transaction` likewise says its rejection paths “commit before raising regardless of caller” (`memory.py:626-632`), and `_retire_within_transaction` refers back to that obsolete exception (`:701-702`). `test_invariant_10_a_version_conflicts_commit_survives_the_outer_rollback_call` and its comments still claim `_reject_version_conflict` already committed and `amend` subsequently called an unconditional rollback (`tests/test_records_memory.py:1645-1677`), but the wrapper now does neither: it records the caught carve-out error and `_commit_or_roll_back` commits in `finally`. This is the exact transaction-ownership contract the structural fix is meant to make unambiguous. Rewrite all of these descriptions to say the helpers only stage and raise, the owning wrapper commits the carve-out, and neutral-core callers retain full rollback control; rename or remove the obsolete “survives outer rollback” test narrative while retaining any non-duplicative behavioral assertion.

2. **[IMPROVEMENT] The stale-source/unknown-target precedence test does not prove that no event of any kind survived, despite claiming it does.** After the setup fetch, `test_an_unknown_target_precedes_the_sources_own_stale_version` says the rejected `retire` committed “no event of any kind,” but only excludes `version_conflict` and `no_receipt` (`tests/test_records_memory.py:284-295`); an erroneous `retire` event or any other unexpected event would pass. The missing-receipt companion correctly asserts an exact empty list, and this stale-version case has one known pre-existing fetch event, so change the assertion to `kinds == ["fetch"]` (or capture and compare the complete pre-call event snapshot). The receipt assertion is already exact, and both tests otherwise traverse the real `retire` ladder and would fail if unknown-target precedence regressed.

VERDICT: NEEDS_CHANGES

### Summary judgment
The revised helper/core docstrings now match the actual implementation: rejection helpers only stage and raise, neutral cores never end transactions, and the transaction-owning wrapper delegates the final code-sensitive decision to `_commit_or_roll_back`. The tightened precedence assertion is exactly correct and materially stronger. The remaining `resolve_latest` branch is unreachable through legitimate M3 behavior with foreign keys enabled and `superseded_by ... ON DELETE RESTRICT`, so declining to manufacture a corrupt store merely for 100% coverage is the right call.

### Findings
1. **[NITPICK] The test identifier still describes an outer rollback that no longer occurs.** `tests/test_records_memory.py:1643` remains named `test_invariant_10_a_version_conflicts_commit_survives_the_outer_rollback_call`, although its corrected body proves that `amend`'s owning `finally` calls `_commit_or_roll_back`, which commits the carve-out; there is no outer rollback call to survive. This is not a remaining claim that `_reject_version_conflict` commits—the docstring and comments now correctly say the opposite—and it does not weaken the test. Optionally rename it to something such as `test_invariant_10_a_version_conflict_is_committed_by_the_transaction_owner`; that preserves the standards-required invariant prefix while making the whole identifier accurate.

No stale prose attributing a commit to `_reject_version_conflict` or `_reject_no_receipt` remains in `zikaron/core/records/memory.py` or the test body. In `test_an_unknown_target_precedes_the_sources_own_stale_version`, `create` emits no event, the single setup `fetch` emits exactly one event for the source, and `amend` emits none, so `kinds == ["fetch"]` is the correct complete expectation and would fail on either a stray kind or a duplicate source event. Exercising `resolve_latest`'s inner `row is None` would require bypassing application behavior—raw deletion of the referenced graph (or mocking/corrupting lookup/FK guarantees); ordinary retire/fetch/amend/create paths cannot produce it, and application connections enable foreign-key enforcement—so no additional test is warranted.

VERDICT: APPROVED
