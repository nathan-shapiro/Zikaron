## Round 1 — 2026-08-01

### Summary judgment
The current singleton data matches the normative documents for all 18 error codes, 22 configuration keys, and 15 event kinds, including ordering, bounds, defaults, payload/detail field order, and store coupling. The package layout, exact direct/transitive pins, and gate configuration comply with the applicable parts of `coding-standards.md` §§1–9; no ignores occur under `zikaron/` or `tests/`. M1 is nevertheless not ready to ship because the central drift guarantee is incomplete and some of its load-bearing Markdown readers do not consistently fail closed.

I could not independently execute `./check.sh` or reproduce the venv because this review session exposes file tools but no process runner. Static inspection confirms that `check.sh` invokes the four required stages, with `mypy --strict zikaron tests` as a strict superset of §9's command, and that every non-comment lock entry inspected is exact-pinned.

### Deliberate-call rulings
1. Type-checking `tests` is an acceptable strengthening of §9, not a violation; the standard need not be amended merely to permit a superset gate.
2. Reading the normative Markdown is the right trade and is materially better than a second transcription, but the present readers need the fail-closed corrections in finding 1.
3. `zikaron/core/events.py` is a defensible cross-cutting home and does not violate the domain layout.
4. `permits`/`accepts` and 5. import-time self-validation are table-owned invariants, not the store/business behaviour excluded by the fence; retaining them is reasonable.
6. `ConfigUnit` is justified by the `seconds int` declarations and the explicit day semantics of `signal_horizon_days`; it is not unsupported schema.
7. Rejecting int-for-float at the schema level is the right unresolved-boundary choice, but `accepts` is not quite as strict as documented (finding 3).
8. Deferring console scripts is correct. Deferring closed event-detail values and the fixed receipt hint is not: they are contract data already present in the M1 tables (finding 2), whereas implementing the later domain operations remains out of scope.
9. Pinning `no_read_receipt` and `no_receipt` independently is correct. They are distinct contracts, and the differing design spellings are not by themselves a design defect.

### Findings
1. **[BLOCKER] The design readers can silently return a plausible but wrong result instead of failing closed.** In `tests/design_tables.py::section_lines`, a second occurrence of the exact same heading executes the `line.strip() == heading` branch before the same-depth termination check, so both sections are accumulated; `first_table` then quietly returns only the first table. A duplicated/revised normative heading can therefore leave the suite checking a stale table. `first_table` also accepts duplicate/empty headers and a delimiter row whose width differs from the header, while `_matching_brace` counts `{`/`[` and `}`/`]` without checking matching delimiter types. Make duplicate target headings an error, require non-empty unique headers and equal header/delimiter widths, and use a delimiter stack for payload groups. Add focused tests in `tests/test_design_tables.py` for duplicate headings, malformed table headers/delimiters, and crossed delimiters; extracting pure line/table parsers or allowing a temporary design root will make those cases hermetic.

2. **[BLOCKER] The purported exact table guards omit contract values that downstream code would otherwise have to re-transcribe.** `zikaron/core/events.py::EVENT_SPECS` records only detail field names, so edits to the closed values for `demotion`, the three per-kind `role` sets, `form`, `phase`, `dense_stop_reason`, or `lexical_stop_reason` do not fail any test. Likewise, `zikaron/core/errors.py::ERROR_SPECS[ErrorCode.NO_READ_RECEIPT]` records a `hint` field but not its required literal `"fetch it first"`; `ZikaronError` currently accepts any hint. This is the exact drift surface M1 exists to close, and postponement would force M3/M5/M7 to introduce fresh literals. Extend the declarative specs with typed closed-value constraints/fixed fields (closed sets should be enums under §2), parse and compare the corresponding design cells/stop-reason table, and have `ZikaronError` enforce or supply fixed fields. Later domain code should consume these definitions rather than restating strings.

3. **[IMPROVEMENT] `ConfigKey.accepts` promises exact Python types but accepts subclasses.** In `zikaron/core/config/keys.py::ConfigKey.accepts`, `isinstance(value, int/float/str)` admits arbitrary subclasses; only `bool` is specially excluded. This contradicts the method contract and the exact-type check used by `__post_init__` and `tests/test_config_keys.py::test_defaults_match_the_design_sample`. Require `type(value) is int`, `float`, or `str` before applying bounds (an accompanying `isinstance` can retain mypy narrowing), and add subclass cases—especially an `IntEnum`—to `test_acceptance_is_strict_about_type`.

VERDICT: NEEDS_CHANGES

## Round 2 — 2026-08-01

### Summary judgment
The remediation is substantial: the original subclass defect is closed, the enum-backed value sets are appropriately colocated with their error/event contracts, and `PayloadField`/`DetailField` are proportionate abstractions. Treating a singleton value set as contract-supplied is also defensible—there is no caller choice to preserve—but its explicit-value validation is not yet type-safe. M1 is not ready to approve because the parser still has ambiguity paths that return stale plausible data, and the event contract still drops design-stated nullability. This review is based on static inspection; this session has no process runner with which to independently rerun `./check.sh`.

### Findings
1. **[BLOCKER] The rewritten readers still accept several ambiguous documents instead of failing closed.** In `tests/design_tables.py::parse_toml`, parsing stops after the first fenced TOML block, so adding a second revised sample under `design/schema.md` §“Configuration keys” leaves the defaults guard checking the stale first copy. In `parse_couplings`, `couplings[name] = severity` silently lets a later duplicate key overwrite an earlier contradictory bullet; `_with_stated_sets` similarly builds a dict that silently overwrites duplicate constraints for one field. Finally, `_structural_headings` does not reject an unterminated fence, so an accidental opening fence after a valid target section can hide every later heading—including a duplicate target heading—while the earlier table/sample still parses successfully. Require exactly one TOML block for `toml_block`, reject duplicate coupling keys and duplicate beside-payload constraints, and reject unbalanced fences before section selection; add literal tests where the stale first declaration agrees with code and the later/hidden declaration disagrees, because those are the cases that prove the guards fail closed rather than merely raise on some malformed input.

2. **[BLOCKER] Round 1’s omitted-contract-values issue was fixed for closed values but moved for nullability.** `design/schema.md` §“The `event` log, per kind” explicitly states that `dense_depth_reached`, `dense_stop_reason`, `lexical_depth_reached`, and `lexical_stop_reason` can be null (lines 585–588), yet `zikaron/core/events.py::_DENSE_STOP`, `_LEXICAL_STOP`, and both kinds’ depth fields retain `nullable=False`. `tests/test_event_kinds.py::test_detail_value_sets_match_the_design_table` compares nullability only against `parse_payload` of the per-kind row, so it cannot see the section’s later normative nullability prose and positively ratifies the wrong value. Mark those fields nullable for `surface_call` and `search`, audit the other explicit null statements in the same table (notably merge/promote size fields), and put the resulting nullability in one machine-readable normative table or add a focused guard for those prose-defined cases.

3. **[BLOCKER] Explicit singleton constants are checked with Python equality rather than wire-value type.** `zikaron/core/errors.py::ZikaronError.__init__` uses `value not in declared.values`; consequently `supported=True` and `supported=1.0` both satisfy the declared integer singleton `(1,)`, but serialize as JSON `true` and `1.0`, not the contract’s integer `1`. This contradicts the documented promise that an explicitly passed fixed field is validated. Make closed-value matching type-aware while retaining the deliberate equivalence between a particular `StrEnum` member and its plain string, and add tests rejecting both boolean and float forms of `schema_incompatible.supported`.

4. **[BLOCKER] Leaving `inactive_row.state` open is the correct non-assumptive implementation choice, but the design gap must be resolved before M1 is finalized.** `design/schema.md` §“Retrieval eligibility—one predicate, three row states” says there are exactly three states, while `design/architecture.md` §“MCP tool surface” supplies the wire spellings `live | superseded | retired`; nevertheless the error row at `design/architecture.md` §“Errors” states only `{uuid, state}`. Closing this error to all three would itself be wrong because an `inactive_row` cannot be `live`; two implementations can currently disagree between `superseded`, `retired`, `retired outright`, or another rendering. Amend the error row to state the intended subset—presumably `state ∈ superseded | retired`—then define a shared row-state enum in the records domain and reference that subset from `ERROR_SPECS`; do not invent an error-local three-value set merely because M10 already names the search result vocabulary.

VERDICT: NEEDS_CHANGES

## Round 3 — 2026-08-01

### Summary judgment
Round 2 findings 1–3 are genuinely closed rather than relocated: the ambiguous readers now reject the identified stale-but-plausible cases, event nullability is guarded from one machine-readable design table, and fixed error values are compared by JSON wire type. The nullability table in `design/schema.md` is a faithful consolidation: each listed field is supported by the pre-existing inline value, arm-null semantics, merge/promote row clauses, or D30 retire query, and I found no omitted or invented null case. Finding 4 remains an open design decision, but `design/build-plan.md` places row lifecycle and the retired-versus-superseded distinction in M3 while M1 is fenced to scaffolding and three declarative tables, so escalation rather than inventing an M1 wire value is appropriate.

### Findings
1. **[NITPICK] Keep the already-escalated `inactive_row.state` decision explicit when M3 starts; no M1 change is warranted.** `design/architecture.md` §“Errors” still leaves the field open as `{uuid, state}`, while §“MCP tool surface” names the broader row-state vocabulary and `design/build-plan.md` §M3 owns the distinction. Resolve the intended inactive subset in the design before implementing M3’s row-state enum; the present exact-value guard will then force `ERROR_SPECS` to follow. This is a downstream design prerequisite, not a defect in the M1 implementation.

VERDICT: APPROVED
