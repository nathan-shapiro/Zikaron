## Round 1 — 2026-08-03

### Summary judgment
The milestone has a strong modular shape, the write-policy drift guard is sound, and the `parse_fenced_code` language-match fix is general: it correctly distinguishes requested, differently tagged, untagged, duplicate, missing, and unterminated fences without changing the DDL reader’s contract. The core failure and lifecycle guarantees are not yet shippable, however: first-run failures can leave no log, successful output is not verbatim, the connection race can create two live services, and tests labeled as catch-all/stdlib enforcement do not exercise those mechanisms. The historical stderr/non-zero narrative is internally consistent and clearly marked as superseded, but several present-tense passages still retain the older silent-failure rule.

### Findings
1. **[BLOCKER] `connect_once` removes the lock and under-lock recheck from the normative start-if-absent algorithm, creating the exact duplicate-service race the lifecycle design prevents.** `zikaron/hook/connect.py`, `connect_once()` and its docstring (roughly lines 88–126), goes directly from an absent first connect to `_vet_and_clear_stale_socket()` and spawn; `design/architecture.md`, “Start-if-absent, without a thundering herd,” requires `flock(<sock>.lock)`, then a second connect before unlink/spawn. Two hooks can both observe absence; after the first child binds, the second hook can vet and unlink that now-live socket, spawn another server at the same path, and leave two services holding one store. The claim that the losing bind merely exits is therefore not sufficient. Keep one **outer** hook attempt, but implement the complete lock/recheck/spawn/poll sequence within it (the second connect under the lock is race resolution, not MCP’s forbidden second outer retry), and add a concurrent cold-start integration test proving only one child is spawned/reachable and no live socket is unlinked.

2. **[BLOCKER] The promised “any failure” handling is not a catch-all, and the test named for an unexpected exception only exercises an explicitly listed exception.** `zikaron/hook/push.py`, `run()` (roughly lines 63–111), performs path setup before its `try` and catches a finite tuple rather than `Exception`; a `RuntimeError` from path/connect/RPC code reaches `main.py`, whose outer suppressor exits 0 but emits neither the required `hook.log` line nor stdout relay. `tests/test_hook_push.py::test_an_unexpected_exception_from_the_socket_is_treated_as_a_transport_failure` uses a malformed response that raises `ConnectionError`, already named in the tuple, so it cannot detect this defect. Wrap all post-suppression setup and work in the degraded boundary, catch a genuine unexpected `Exception` after the specific rejection handling, classify it without logging its message, and add a test that monkeypatches a dependency to raise `RuntimeError` and asserts one log line plus the relay. The same robustness gap exists on `agentSpawn`: `zikaron/hook/spawn_warm.py`, `run()` / `_spawn_warm_helper_best_effort()` (roughly lines 27–63), suppresses only `OSError` around `Popen`, while path derivation and other spawn exceptions can escape and cause `main.py` to suppress the write policy itself; catch the entire best-effort warming operation and test a non-`OSError` without changing policy output.

3. **[BLOCKER] `hook.log` is not guaranteed on first-run/pre-spawn failures, and its claimed exact `0600` creation is not umask-independent.** `zikaron/hook/failure.py::record_failure()` (roughly lines 18–50) calls `os.open` without creating or securely validating the parent `.zikaron` directory. On a fresh project, a hostile runtime directory or `Popen` failure occurs before the service creates `.zikaron`; `os.open` gets `ENOENT`, is swallowed, and no required record exists. `tests/test_hook_main.py::test_a_degraded_user_prompt_submit_still_exits_zero_and_relays_on_stdout` constructs exactly that absent-`.zikaron` case but never asserts the file, while `tests/test_hook_failure.py::test_never_raises_when_the_parent_directory_does_not_exist` explicitly accepts losing the record. Also, POSIX applies the process umask to the `0o600` argument (`mode & ~umask`), so a restrictive umask can create `0000`; the docstring’s “umask-independent” assertion is false. Securely create/vet `.zikaron` at `0700` before logging (reuse a verified stdlib-thin permission helper or implement the same symlink refusal), set a restrictive creation umask or `fchmod` a newly created descriptor to exactly `0600`, and add fresh-project, symlink/hostile-parent, and restrictive-umask tests that assert one exact line. The line formatter itself does not expose prompt or memory content: it receives only a classified kind and optional integer.

4. **[BLOCKER] The real entry point does not print successful service text verbatim and violates the documented empty-store behavior.** `zikaron/hook/main.py::_run()` ends with `print(output)`, which appends a newline not returned by `surface`; for `surface` returning `""`, it emits `"\n"` even though `design/architecture.md`, “Errors” (around line 1532), says an empty `surface` prints nothing at all. The same extra byte means the agentSpawn constant is not emitted exactly as held. Replace `print(output)` with `sys.stdout.write(output)` (while retaining `None` as suppression), and add entry-point tests asserting byte-for-byte non-empty surface output and `stdout == ""` for a successful empty result. Current tests compare `push.run()` directly or merely check that the subprocess policy output contains a phrase, so they miss the process-level transformation.

5. **[BLOCKER] The detached warm helper cannot warm a genuinely new project.** `zikaron/hook/warm_helper.py::run()` (roughly lines 69–91) calls `_configure_warmup_log(<cwd>/.zikaron/warmup.log)` before its `try`; `_configure_warmup_log()` begins with `Path.touch()`. If `.zikaron` does not exist—the ordinary first-session state—this raises `FileNotFoundError`, exits the detached helper before start-if-absent, and produces no warmup log. Every warm-helper test pre-creates either the directory or a complete store, so the real first-run path is absent. Ensure the store directory exists through the shared symlink-refusing `0700` validator before configuring the log, include setup inside the helper’s failure boundary where possible, and add an integration test starting from a cwd with no `.zikaron` that observes a reachable service. While fixing this, reconcile `_configure_warmup_log()` / `run()` with `design/architecture.md`’s filesystem table: `logger.exception("warm failed")` records arbitrary exception text/tracebacks and success records path/id, contradicting the claim that `warmup.log` contains only fixed labels and an error code; either log only the stated fixed fields or explicitly narrow the design’s security claim after proving no sensitive values can enter it.

6. **[BLOCKER] Store-identity and local-error reporting are not implemented end to end.** `zikaron/hook/push.py` always passes `store_id=None` to `connect_once` (roughly lines 84–89), including for an existing store, so the store-id mismatch branch is unreachable from the production hook despite `design/architecture.md`, “Store identity is verified, not assumed,” reserving path-only verification for a store that does not exist yet. In addition, `connect.py::_verify_identity()` raises `HookTransportError`, and `push.py::_classify_failure()` maps every such error to `transport`, so even a path mismatch is not logged as `store_identity`; a local `ZikaronError` returns its wire name but drops its available numeric `ErrorCode` (for example hostile-runtime `bad_config` loses `-32023`). Decide and document how an ephemeral no-store-read hook can satisfy identity—either define its every invocation as path-only with an explicit design exception, or provide a non-store identity source—then preserve `store_identity/-32030` and local numeric codes in classification. Add push-level tests for identity mismatch and hostile-runtime exact `(kind, code)` lines; the current connect-only mismatch tests and substring-only hostile-runtime assertion do not cover the observable contract.

7. **[BLOCKER] `test_hook_stdlib_only.py` is a dependency denylist, not a test of the claimed stdlib-only invariant.** `_FORBIDDEN_TOP_LEVEL_PACKAGES` (roughly lines 43–54) catches only nine anticipated names; importing any other third-party package (for example `requests`) would pass while violating the milestone. `_CRITICAL_PATH_MODULES` is also hand-maintained, so a new hook module is silently exempt until someone remembers to edit the test—the opposite of the test’s enforcement claim—although the current list does exempt only `warm_helper.py`. Discover all `zikaron/hook/*.py` modules and assert the discovered set equals the tested set minus exactly `warm_helper`; in a fresh interpreter, classify every newly loaded top-level module as stdlib, `zikaron`, or forbidden third-party (or use a static recursive import-origin check), while retaining the dedicated `logging` assertion. Add a small self-test fixture/module proving an arbitrary third-party import makes the enforcement fail.

8. **[BLOCKER] The required stale-contract sweep still finds present-tense statements of the superseded silent-failure behavior.** Concrete stale sites are `design/architecture.md`, “Store identity is verified” around line 480 (`nothing printed`); `design/write-policy.md` around line 266 (`nothing printed, nothing read, one line`); `design/schema.md` around lines 332, 360, and 679 with the same current-rule wording; `zikaron/hook/failure.py` module docstring lines 3–5 and `record_failure()` docstring around line 28; and `zikaron/hook/connect.py` around lines 50 and 69 (`degrade silently` / quoted `print nothing`). `design/build-plan.md` line 290 is also ambiguous: “agentSpawn … print nothing on failure” can be read as suppressing the policy, whereas the final contract says warming failure adds no output but never removes the policy. Replace each current-rule statement with “one `hook.log` line plus exit-0 stdout relay” (or clarify subagent/agentSpawn-only silence). The architecture and `push.py` historical narratives accurately describe total silence, then stderr/non-zero, then the measured final shape; those explicitly historical references should remain.

9. **[IMPROVEMENT] Several default-tier tests violate the project’s own three-tier rule for real UDS work.** `tests/test_hook_connect.py`, `test_hook_connect_edge_cases.py`, and `test_hook_push.py` bind and communicate over real `AF_UNIX` sockets but carry no `integration` marker, while `design/coding-standards.md` §4 explicitly assigns a real UDS socket to integration. Either mark those tests integration and retain cheaper pure unit tests for classification/control flow, or amend §4 to distinguish in-process socketpair/background-thread fakes from subprocess service integration; the tests currently assert a tier interpretation opposite to the binding standard.

This is useful evidence in `design/architecture.md`, where it already lives, but conflicts with `coding-standards.md` §5’s “no circumstantial provenance” and “docstrings state the contract” rules. Keep a concise timeless reason in code (non-zero suppresses the working stdout channel on the supported harness, so failures use exit-0 stdout plus a fixed-detail log) and leave the revision history and experiment narrative in the design document.

## Round 2 — 2026-08-03

### Summary judgment
The catch-all failure handling, first-run log creation and permissions, byte-exact stdout, fresh-project warming, positive stdlib enforcement, and test-tier clarification are real fixes in the current files. The lock implementation itself now follows the under-lock recheck sequence, but its new tests do not prove that mechanism, and the identity fix introduces a direct SQLite read that contradicts the milestone's critical-path contract and can defeat both identity verification and the deadline. Several round-1 requirements also remain only partially addressed, so this is not ready to ship despite the reported green gate.

### Findings
1. **[BLOCKER] The new race tests would pass if the lock were removed and do not prove “exactly one spawn”; they also leave the spawned fake server unreaped.** `zikaron/hook/connect.py:135-186` now contains the right `flock` and under-lock recheck, but `tests/test_hook_connect_race.py:109-142` asserts only that two callers return sockets. Without a lock, both callers can spawn the delayed script, one child can win `bind()` while the other exits, and both callers can connect to the winner—exactly the asserted outcome. The second test (`tests/test_hook_connect_race.py:154-207`) starts a live listener before either caller's initial connect, so both take the warm fast path even in the old lock-free implementation; checking that a pathname exists does not prove that the original socket inode was never unlinked and replaced. The delayed child also remains alive until its five-second accept timeout, with no PID capture or `waitpid`. Instrument the spawn command to append each child PID/start to a marker, assert exactly one start, terminate and reap every recorded PID, and add a coordinated race in which one caller misses initially while another binds before the under-lock recheck; assert the original socket inode remains and the losing caller never invokes spawn.

2. **[BLOCKER] The store-identity fix violates the hook's no-store-access invariant, can outlive the two-second budget, and fails open on an existing unreadable store.** `zikaron/hook/push.py:76` calls `connect.read_existing_store_id`, whose `sqlite3.connect` is at `zikaron/hook/connect.py:339-379`. This directly contradicts `design/architecture.md:721-746` (“never a reader,” “Never open the store”), `design/build-plan.md:298` (“no direct store access under any circumstance”), and `design/retrieval.md:648` (“never opens the store”). It also uses sqlite3's default multi-second busy timeout before `push.py:83` checks elapsed time, so a locked database can already have exceeded the nominal two-second hook deadline; and every sqlite error, absent table, or absent row becomes `None`, which `_verify_identity` interprets as the one legitimate *nonexistent-store* bootstrap case. There is even an existence/open race in which bare `sqlite3.connect` can recreate a just-deleted `memory.db`. Choose a mechanism consistent with the normative design (for example a securely created identity sidecar, or an explicitly documented path-only hook exception); if direct SQLite access is intentionally retained, revise every no-store contract, use read-only/non-creating bounded access, account it inside the deadline, and make an existing-but-unreadable identity degrade rather than silently skip comparison. Add locked, malformed/missing-meta, and deletion-race tests.

3. **[BLOCKER] Local `ZikaronError` codes are still dropped, leaving round-1 finding 6 partially unresolved.** `zikaron/hook/push.py:143-150` returns `(error.code.wire_name, None)`, even though the error carries an `ErrorCode` and the degraded contract requires the numeric code “where one exists.” Consequently the hostile-runtime `BAD_CONFIG` path logs `bad_config` without `-32023`; `tests/test_hook_push.py:362-391` checks only the label and cannot catch the omission. Return `str(error.code.wire_name), int(error.code)` and make that test assert one exact line containing both `bad_config` and `-32023` (while retaining the separate wire-rejection test).

4. **[BLOCKER] The stale-contract sweep is not complete, and lifecycle prose now also contradicts the hook's single-attempt implementation.** `design/schema.md:332` still says that on `bad_config` the hook “prints nothing and reads nothing,” and `design/architecture.md:598-600` still calls the hook fallback “a degraded mode with no answer at all” and a “silent-failure requirement.” Those are present-tense statements of the superseded contract, not subagent suppression or empty successful retrieval. The same architecture passage says “Clients retry once through the full start-if-absent,” while `zikaron/hook/connect.py` and its tests deliberately guarantee one outer hook attempt. Replace the stale output text with the `hook.log` plus exit-0 stdout relay, and distinguish the MCP client's retry from the hook's single outer attempt.

5. **[BLOCKER] `warmup.log` still violates the filesystem-security and erasure contracts on successful warming.** `zikaron/hook/warm_helper.py:112` writes `health.store_path` and `health.store_id`, while `design/architecture.md:509` and `design/write-policy.md:171-172` say the file contains nothing beyond a fixed failure-kind label and error code and therefore cannot retain sensitive text. Changing `logger.exception` to `logger.error` fixes the failure traceback only; `tests/test_hook_warm_helper_integration.py` merely looks for `service warm` and does not reject the variable suffix. Log fixed status labels only (for example `service_warm` / `warm_failed`) and test that neither supplied path/id nor exception text appears, or explicitly revise the security and erasure claims after assessing path disclosure.

6. **[BLOCKER] The claimed agentSpawn process cleanup is bounded in the wrong direction and does not verify termination.** `_reap_any_service_spawned_for` waits only five seconds and returns if no service is visible (`tests/test_hook_main.py:160-190`), while the detached warm helper's own start-if-absent deadline is ten seconds; on a slower machine the helper can therefore create a service after cleanup has already given up. When a PID is found, `os.waitpid` at lines 193-200 cannot reap this service because it is a grandchild of the test process, so `ChildProcessError` causes an immediate return without checking that SIGTERM actually stopped it; there is no SIGKILL escalation or failing assertion. ## Round 4 — 2026-08-03

### Summary judgment
Removing the warm helper's direct SQLite read is complete in the current production and test call graph, and the new busy-store test genuinely isolates inode drift from idle timeout because `in_flight` remains nonzero. A replacement after the lifecycle task captures its baseline is detected on the first poll, and ordinary SQLite WAL/checkpoint work does not replace the main database directory entry, so it does not spuriously change the inode. The implementation is still not shippable because the captured inode is not actually proven to be the inode held by SQLite: a replacement between store open and the lifecycle coroutine's first execution is accepted as the baseline and then evades detection forever.

### Findings
1. **[BLOCKER] The inode baseline has an open-to-task-start race, so it can record the replacement inode rather than the inode the service is serving.** `zikaron/service/main.py:171-184` opens the store in `_assemble_or_log_and_raise`, then binds the server, and only then schedules `idle_self_stop`; an `asyncio.create_task` does not run the coroutine body synchronously. `zikaron/service/lifecycle.py:89` later obtains `ctx.store.path.stat().st_ino` from the *current pathname*, not from SQLite's already-open file descriptor. If `memory.db` is replaced after SQLite opens the old file but before line 89 executes, line 89 records the new file's inode, every later poll sees that same new inode, and the service continues serving the old unlinked database indefinitely. `ServiceContext` having been constructed after `Store.open/create` proves only that SQLite opened first; it does not prove that a later pathname stat still identifies that open file. The present replacement tests deliberately do the opposite ordering (`tests/test_service_lifecycle.py:37-42,83-86`): they sleep in the hope that capture has happened and only then replace the path, so they cannot detect this race (and the timing sleep is itself nondeterministic). Establish and retain a filesystem identity tied to store opening—preferably `(st_dev, st_ino)` captured with a file descriptor held across SQLite connection creation plus a post-open path comparison, or another mechanism that actually identifies SQLite's open file—and put that immutable baseline on `Store`/`ServiceContext`; reject or retry startup if the pre/post identities drift. Then have `idle_self_stop` consume that baseline rather than stat for the first time, and add a deterministic regression test that opens the context, replaces `memory.db` **before** starting `idle_self_stop`, and still observes shutdown within one poll.

2. **[IMPROVEMENT] The path-only exception is not propagated consistently through the remaining normative and API text.** `zikaron/hook/warm_helper.py:102-106` now correctly passes `store_id=None` unconditionally, including for an existing store, but `zikaron/service/lifecycle.py:224-238` still defines `None` as only “this store does not exist on disk yet”; `zikaron/hook/connect.py:194-197` and `tests/test_hook_connect.py:98-103` repeat that obsolete meaning. `design/architecture.md:558` also still says both thin clients verify both `store_id` and `store_path`, without qualifying the explicit hook exception at lines 498-512. The architecture's new exception paragraph does mention that the detached warm helper's direct read was rejected, so the intended behavior can be reconstructed, but these other passages still describe the production calls as contract violations. Define `None` consistently as “this caller has no independent store ID,” explicitly name both `userPromptSubmit` and the detached warm helper as permanent path-only callers, and qualify lifecycle step 6 with the identity section's client-specific rule. Update the test name/docstring to pin the permanent hook behavior rather than the old nonexistent-store bootstrap case.

3. **[IMPROVEMENT] `_store_path_now_differs` treats every stat error as replacement while its own text and the design claim only absence or inode mismatch.** `zikaron/service/lifecycle.py:100-109` catches all `OSError` and returns `True`, so `PermissionError`, `EIO`, or another non-absence stat failure causes immediate shutdown. Its docstring simultaneously says a transient stat failure should wait for “the very next poll,” which the implementation makes impossible by exiting on this poll; `design/architecture.md:613-632` specifies a missing path or changed inode, not arbitrary stat failure. A WAL checkpoint is not a problem here—it writes the existing main file and WAL rather than swapping the main pathname's inode—but the broad exception branch is a separate false-positive policy. Either catch only `FileNotFoundError` and define how other errors are surfaced/retried, or deliberately fail closed on every inability to stat and state that policy consistently in the helper and architecture.

4. **[IMPROVEMENT] The claimed provenance cleanup is still visibly incomplete in the current hook files.** `zikaron/hook/connect.py:112-113` still says “the distinction the user asked this module to hold,” and `zikaron/hook/push.py:14-15` still says the measurement overturned “two earlier designs.” Both are exact circumstantial-history forms already identified in round 3 and prohibited by `design/coding-standards.md` §5. The current full-package grep also finds `zikaron/hook/failure.py:35` calling a helper “already-reviewed”; remove that provenance adjective while doing the promised sweep.

## Round 5 — 2026-08-03

### Summary judgment
The `store_id=None` text is now consistent with the hook's permanent path-only exception, the provenance phrases are gone from the reviewed production files, and `FileNotFoundError` is the right narrow signal for an absent final path while unrelated `stat` failures remain genuine errors. The new lifecycle test non-coincidentally proves that `idle_self_stop` honors a baseline captured before that task exists, but it does not prove that production captured the inode SQLite actually opened. The open-to-baseline race therefore remains across the internals of `Store.open`/`Store.create`, and the claimed main-level propagation of every unexpected stat failure also has one concurrent-signal hole.

### Findings
1. **[BLOCKER] Moving the pathname `stat` to the statement after `ServiceContext.assemble()` does not tie the baseline to the file SQLite opened, and the design's “no `await` between the store opening and that read” claim is false across the actual call graph.** `zikaron/service/main.py:171-182` does make the `stat` the next statement after `_assemble_or_log_and_raise()` returns, but `ServiceContext.assemble()` opens the store inside that awaited call (`zikaron/service/context.py:151`). On the existing-store path, SQLite opens `memory.db` at `zikaron/core/store/store.py:405` and then `_validate_on_open()` performs multiple awaited SQL operations at line 407 before returning; on creation, SQLite opens it at line 323, then table/meta creation and permission work await repeatedly from lines 325 onward. A replacement after `_open_connection()` has opened the original but before `assemble()` returns is therefore still adopted by `main.py` as the baseline while SQLite continues serving the original. Even without those internal awaits, “no `await`” only prevents another coroutine on this event loop from running; it does not make the pathname read atomic against the external process that can unlink and recreate the database. `tests/test_service_lifecycle.py:63-94` is sound for its narrower assertion—`in_flight=1` excludes an idle exit, and replacement precedes task creation—but it manually captures the correct inode only after `open_context()` has fully returned, so it structurally bypasses the production interval at issue and would still pass with the race above. Establish the immutable `(st_dev, st_ino)` baseline in `Store.open`/`Store.create` as part of connection establishment, retain it on `Store`/`ServiceContext`, and have `main.py` consume that value rather than re-stat the pathname. A practical implementation should pin the pre-open file with a descriptor (preventing inode reuse), compare the pathname again after SQLite's awaited open/validation, and reject/retry startup on drift; the create path needs an equivalent pinned creation sequence. Add a deterministic production-level regression that replaces `memory.db` after `_open_connection()` succeeds but before `_validate_on_open()`/creation returns, then proves startup rejects the drift or the service self-stops using the original identity. Update `design/architecture.md:626-639` only after the baseline is genuinely tied to SQLite's open file.
