### Summary judgment

The decision is well-grounded — every harness behaviour the design leans on was measured, the fail-open and override reasoning is sound, and the installer selection is coherent with the existing ownership-by-command and per-trigger merge logic in `targets.py` (a `guards` install preserving memory triggers, and vice versa, falls out of `_plan_settings`' "triggers not in ours are copied verbatim" shape). ### Findings

1. **[BLOCKER] The override must withdraw the deny, not grant approval — `design/edit-guards.md` §3.3, and the brief's live-test bullet.**
   §3.3 says a command carrying the marker "is allowed", and the probe (`research/claude-code-tool-hook-probe.md` §Hooks) implemented that as `permissionDecision: "allow"` plus `additionalContext`. Per the docs note §3.2 [RAW], `allow` "skip[s] the interactive permission prompt" — so in `default`, `acceptEdits` and `auto` modes an agent that appends `#ZIKARON-FORCE #Reason: fix file` to `python3 -c "open('x','w').write(…)"` also skips the prompt or classifier the user's own policy would have applied to that command. A guard installed to *tighten* edits would loosen Bash approval on exactly the commands it exists to watch. The probe could not see this because it ran under `bypassPermissions`. Fix, one sentence in §3.3: *"On a valid override the hook emits **no `permissionDecision`** — exit 0, JSON carrying only `hookSpecificOutput.hookEventName` and the acknowledging `additionalContext` — so the harness's own permission flow decides exactly as if no guard were installed; the override withdraws the deny and grants nothing."* Then in §2's table, mark the `allow` + `additionalContext` row as what was measured and add that delivery of `additionalContext` **without** a decision is unmeasured; and in the brief's live test add *"the acknowledgement arrives on the no-decision path; if it does not, drop the acknowledgement rather than restore `allow`"*. §6's fail-open already uses "no output" = no decision, so this makes the two paths consistent.

2. **[BLOCKER] §3.1–§3.3 are forms, not rules; a test table cannot be written from them without deciding six things — `design/edit-guards.md` §3.1, §3.2, §3.3.**
   Each item below is a decision the brief's "parametrised table of commands with their expected decision" needs before its first row, and each has a cheap regex-only answer that stays inside §1. Write them into the spec:
   - **(a) Command-word position, rows 1–3 and 5.** As written, `sed -i` matches anywhere, so `grep -rn "sed -i" tests/` — the sweep this project's own `CLAUDE.md` demands after every edit, and which M37's own build will run many times — is a false deny on every call. Rule: the command word (`(\S*/)?g?sed`, `perl`, `g?awk`, `cat|echo|printf|tee`) matches only at line start or after `|`, `;`, `&`, `(`, `` ` ``, `$(`, or after one of a stated wrapper set (`sudo`, `env`, `xargs`, `time`, `nice`, `command`, `exec`, `-exec`). A heredoc body line that *starts* with `sed -i` is still caught, which is right.
   - **(b) What a short-flag cluster is, rows 1–2.** "`i` inside a short-flag cluster" denies `perl -Mstrict -pe …` and `perl -Ilib …` (`i` inside an attached argument). Rule: a whitespace-delimited token `-<letters>` in which `i` is preceded only by letters that take no argument — sed `[nrEsuz]`, perl `[pnlawsc]` — case-sensitive, so `-I` never counts; `-i` may carry an attached suffix. State the two alphabets in the table.
   - **(c) Row 4's interpreter word and write-call list as patterns.** `python3.12 -c`, `.venv/bin/python -c` and `uv run python -c` all occur here; the word is `(\S*/)?(python[0-9.]*|node|ruby)`, inline is `-c`/`-e` or `<<` on the same line. `open(…, 'w'` must be a pattern covering both quote styles and the keyword form: `open\([^)]*['"](w|a|x|r\+)` and `mode\s*=\s*['"](w|a|x|r\+)`. Either add `writeFile(` (node's async form) or say the three node names are deliberately the whole set.
   - **(d) Row 5's heredoc form must not scan the body for its sink.** `gh pr create --body "$(cat <<'EOF' … > quoted line … EOF)"` is the idiom `CLAUDE.md` requires for every PR, and a `>` in a Markdown body (`> note`, `->`, `=>`) is routine; with the sink matched anywhere it is a false deny on the one command that ends every milestone. Rule: for the heredoc form, `>`/`>>`/`| tee` is matched on the heredoc's **opening line** only; the body is never scanned for row 5. Say explicitly that rows 1–4 *do* scan the body (`bash <<EOF … sed -i … EOF` and the python heredoc depend on it).
   - **(e) Which tokens are §3.2's targets, per form.** "Every one the matched form names" is not extractable by a regex that does not know which token is the script. Either state per form — rows 1–3: every non-`-` token after the command word except the first (the script), unless `-e`/`-f`/`--expression`/`--file` is present, in which case every non-flag token; row 5: the token after `>`/`>>` or after `tee [-a]`; row 4: the first string literal inside `open(`/`Path(` — or adopt the conservative rule *exempt iff at least one absolute-path-looking token exists and every such token is scratch*. Pick one; the expected decision for `sed -i 's|/usr|/opt|' /tmp/x` differs between them, and the test table has to say which.
   - **(f) The marker's boundary and scope.** State that the override is examined only after a row matched (`ls #ZIKARON-FORCE` allows — §3.3's bare-marker bullet reads as if it denies anything), that the marker must be preceded by whitespace or line start (`(^|\s)#ZIKARON-FORCE\s+#Reason:[ \t]*(\S+[ \t]+\S+)`) — otherwise `f#ZIKARON-FORCE` is part of the filename to the shell and "the shell ignores it" is false — and that "words" are whitespace-delimited tokens on the marker's own line.

### Findings

1. **[IMPROVEMENT] The override can be satisfied from inside a heredoc body — `design/edit-guards.md` §3.4 ("a match, on any line of the command").**
   The body of `cat > tests/test_guard_rules.py <<'EOF' … EOF` or `cat > README.md <<'EOF' … EOF` will, in this repository, contain the literal `#ZIKARON-FORCE #Reason: <few words>` — the fixtures and the documentation for the guard itself — and §3.4 as written matches it there: row 5 fires, the target is not scratch, and the override regex finds a marker preceded by whitespace with two words (`<few`, `words>`) after it. The hook then returns no decision and an `additionalContext` acknowledging a reason the agent never gave, and the agent never sees a deny on exactly the files M37 produces. The heredoc parse already exists for the row 1–4 body scan, so the fix is one sentence in §3.4: *"The marker is matched only on lines that are not heredoc bodies (§3.2); a marker inside a body is content, not an override."* Add the row to the brief's table: a heredoc write whose body contains a valid-looking marker → deny.

2. **[IMPROVEMENT] Command position misses the loop and the conditional — `design/edit-guards.md` §3.1.**
   `for f in *.md; do sed -i 's/a/b/' "$f"; done` is the bulk mechanical change §3.4 names as the override's reason for existing, and the guard never fires on it: after `;` comes `do`, which is in neither §3.1's position list nor its wrapper list, so `sed` is not in command position. Likewise `if grep -q x f; then sed -i … f; fi`, `while read f; do perl -pi -e … "$f"; done`, and `elif`. Add `do`, `then`, `else` and `elif` to the tokens after which a word is in command position. In the same sentence allow leading `NAME=value` assignments *without* `env` — `LC_ALL=C sed -i …` is a real idiom and is a miss today, since only `env` with assignments is a wrapper. Test rows: the `for` loop (deny), the `if/then` (deny), `LC_ALL=C sed -i 's/a/b/' f` (deny).

3. **[IMPROVEMENT] The live test's permission mode is unstated, and in the tier's existing mode its override half cannot pass — `design/build-plan.md` §M37, "A live test".**
   `tests/test_install_claude_live.py::_turn` runs `claude -p <prompt>` with no `--permission-mode`, i.e. headless `default`. The probe's second run records what a no-decision `sed -i` gets under `default`: *"needs approval"* — and in `-p` there is no host to approve, so the file does not change. The brief asserts "the override runs, changes the file". Write into the bullet: the session runs under `--permission-mode bypassPermissions`, as the probe did; in that mode the deny holding is itself one of §2's measured rows and is asserted; and **what the live test cannot show there** — `allow` and no-decision are indistinguishable under `bypassPermissions` — is held by the hermetic test on the hook's JSON (no `permissionDecision` key on the override path), so the live assertion for the override is the file change plus the acknowledgement attachment and nothing about the permission flow.

4. **[IMPROVEMENT] BSD `sed -i ''` makes every scratch edit on macOS a false deny — `design/edit-guards.md` §3.3, rows 1–3.**
   D35 supports macOS arm64, where `/usr/bin/sed` requires a suffix argument after `-i` and the universal idiom is `sed -i '' 's/a/b/' f`. Under §3.3's target rule the first non-flag token — `''` — is taken as the script, so `'s/a/b/'` becomes a target and `sed -i '' 's/a/b/' /tmp/x` is not exempt. Every scratch edit on that platform then needs an override, which is the reflexive-use pattern §7(c) exists to detect. Add to the exclusion list: *"and, for a bare `-i` token, an immediately following empty quoted string (`''` or `""`), BSD sed's suffix argument."* Test rows: `sed -i '' 's/a/b/' /tmp/x` → allow; `sed -i '' 's/a/b/' f` → deny.

5. **[NITPICK] Flag clusters ending in `e`/`f`, and perl's `-E` — §3.3, rows 1–3.** The rule names `-e`/`-f` as the flags whose argument is excluded and whose presence stops the first-token drop, but §3.2's own examples use `-pe`, and `sed -ne` is common. State: *"a cluster whose last letter is `e` or `f` takes the next token as its argument and counts as `-e`/`-f` being present"*, and add perl's `-E`.

6. **[NITPICK] The guard timeout is a named constant with no number — §5.** "A constant in `zikaron/guard/`" tells a reader nothing about the worst case, which is the stall every Bash call and every edit pays while a wedged interpreter is waited for. Name it — `HOOK_TIMEOUT_SECONDS` (10 s) reused, or a smaller figure stated here — so §6's "bounded" has a bound.

Either correct the sentence, or have M37 extend that test to resolve every declared script, so a `zikaron-guard` entry naming a module that does not exist fails.

8. **[NITPICK] §2's no-decision row conflates two runs.** Delivery of `additionalContext` on the no-decision path was measured under `bypassPermissions` (the nonce was quoted); under `default` the probe records the approval outcome only, not whether the nonce arrived. 11. **[NITPICK] Gaps the test table needs an expected value for — §7.** State each as a miss or a false deny, so the builder does not decide it silently: `bash -c '…'`/`sh -c '…'` (the quoted script is one token: miss); a backslash-newline continuation (`find … \` then `-exec sed -i …` — as written `-exec` alone at line start is not a wrapper: miss, or make `-exec`/`-execdir` wrappers on their own); `cd dir && sed -i … f` (`f` resolves against the pre-`cd` cwd: false deny); `{ echo a; echo b; } > f` and `echo x | cat > f` (miss); `&>`, `>|` and `1>` (miss — and §3.1's "a digit followed by `>` … is never a sink" is false of `1> f`, which writes `f`; harmless, but say "not treated as a sink"); the delimiter of `<<'EOF'` compared with its quotes removed, and `<<-` with leading tabs stripped; the PR-body false deny generalised from row 1 to rows 1–4 (`python3 -c "open('f','w')"` quoted at line start in a code block); node's `--eval`/`-p`; and row 4's `"/"` literal (`s.split("/")` makes an otherwise scratch-only script non-exempt).

### Findings

1. **[IMPROVEMENT] An unquoted `#` comment's words become rows 1–3's targets — `design/edit-guards.md` §3.1, §3.3.**
