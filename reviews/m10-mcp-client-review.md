## Round 1 — 2026-08-03

**Summary judgment:** The core shape is strong: each mode builds one FastMCP instance with only its own tools, the implemented signatures and `apply_*` wire names match the architecture, the sequential `plan_groups` transitions match the three-state table, and create-on-absent does not recreate a `memory.db` that already exists. **Findings:**

1. [BLOCKER] `zikaron/mcp/connection.py::client_envelope` and `ServiceConnection.request` never implement the response-label adoption required by `design/architecture.md` §“The request envelope — where session_id comes from.” With no `KIRO_SESSION_ID`, every call sends `session_id: null`; `_send` returns the top-level `client.session_id` supplied by the service, but no code reads it, and the next call bootstraps a different label. This is functional breakage, not only observability drift: `fetch` mints a receipt under label A and `amend` presents label B, while a consolidator’s successful `plan_groups` is owned by `(A, pid)` and its immediately following `next_group` arrives as `(B, pid)` and can report `{busy: true}` against its own run. The same helper also forwards a harness-provided `KIRO_SESSION_ID` beginning with reserved `zk-`, contrary to the explicit client namespace contract. Give the process/connection stable session state, treat absent or `zk-`-prefixed environment values as bootstrap, validate and adopt top-level `client.session_id` from every success and application-error response before returning/raising, and use the adopted value in every later envelope. Add tests for an env-less `fetch`→`amend`, env-less consolidator `plan_groups`→`next_group`, adoption from a first error response, and reserved-prefix handling; the current MCP tests never inspect response-envelope labels.

2. [BLOCKER] `zikaron/service/main.py::_ensure_store_dir_exists` uses bare `mkdir(..., exist_ok=True)` and `run` immediately opens `service.log` through that path before `ServiceContext.assemble` reaches `permissions.ensure_store_dir`. A `.zikaron` symlink to another directory therefore passes the mkdir call and receives a log write before the required “refuse a store reached through a symlink” check; an existing wide directory is likewise used before being tightened. This contradicts `design/architecture.md` §Filesystem security even though it fixes the intended first-run log ordering. Replace the bare helper with the store permission/path validator (or equivalent no-follow validation plus `0700` creation) before configuring the log, while preserving “directory first, log second, assembly third.” Add a test with `.zikaron` symlinked outside the cwd that asserts startup rejects it and creates no `service.log` in the target, plus a mode test for a newly created directory.

3. [BLOCKER] `zikaron/mcp/consolidator.py::_PlanBridge.ensure_planned` does not make “at most once successfully per process” atomic. Two concurrent first `zikaron_next_group` calls can both observe `UNPLANNED` before either awaits `connection.request`; initial connection establishment itself awaits `_read_store_identity`, so FastMCP scheduling can let both proceed to separate successful `plan_groups` calls. That permits two takeovers by one process and violates the exact done-when bound. Protect the transition with an `asyncio.Lock` and re-check `READY`/`FAILED` after acquiring it; also serialize `ServiceConnection`’s first-connect/socket ownership so concurrent calls cannot create two sockets and leak the overwritten one. Add a barrier/sleep-controlled `asyncio.gather` test proving two simultaneous first serves produce exactly one `plan_groups` success and then two forwarded `next_group` calls.

4. Catch and wrap `ZikaronError` at both MCP boundaries (and record `FAILED` in the bridge), preserving its code/data in the visible message where possible. Exercise this through `fastmcp.Client`, not only by calling helpers directly, so the test proves the model receives an ordinary tool error and that a second bridge call does not retry.

Both claim `FastEmbedEncoder.load` fails “after a successful `Store.open`,” but `ServiceContext.assemble` was changed to load the encoder before `_open_or_create`; the monkeypatch therefore raises before this invocation opens any store, and the pre-created store was already closed by the fixture setup. The close-failure variant consequently never calls its patched `Store.close` either. Trigger failure in a genuinely later construction step (for example, patch `IndexingContext.for_store` after supplying a successful fake encoder and letting `_open_or_create` return a tracked real store), assert the close spy was called, and retain the leak fixture as a second line of evidence. Make the close-failure test assert that its raising close path was actually reached as well as that the original construction error survived.

6. [IMPROVEMENT] The MCP tests do not lock down the exact contracts the milestone says are normative. `tests/test_mcp_server.py` checks tool-name sets but not generated input schemas/defaults or exposed descriptions; `tests/test_mcp_consolidator_bridge.py` verifies only `next_group` forwarding; no named test proves the five primary methods and three consolidator write tools send the exact method/parameter dictionaries (`apply_merge`, `apply_promote`, `apply_discard`) and client kinds. Add parameterized in-memory `fastmcp.Client` calls with a recording `ServiceConnection.request` for all nine tools, asserting method, params, kind, and unchanged result/conflict shape, and assert schemas/defaults plus the decision-critical description clauses. Patch the actual service-reaching seams (`connect_start_if_absent` and store open/read, or the low-level connect) to fail, and run both server construction and `tools/list`; keep the request spy as a complementary assertion rather than calling it proof by itself.

8. [IMPROVEMENT] `zikaron/mcp/connection.py::ServiceConnection.request` blindly retries every method after an ambiguous disconnect, while `client_envelope` sends `op_id=None` and the service mints a new operation id on each attempt. If `remember` commits and the service dies before its response reaches the client, the retry can create a second memory; the current integration test kills only between completed calls and cannot distinguish this from safe recovery. The architecture requires one retry but does not state the resulting at-least-once mutation semantics. Resolve this explicitly in design and code: either add true server-side idempotency keyed by a client-minted operation id retained across the logical call, or constrain retries to failures known to precede request acceptance and document how ambiguous mutating failures surface. Add a fault-injection test that commits a write and drops its response.

## Round 5 — 2026-08-03

**Summary judgment:** The Round 4 finding is fixed correctly: the established socket is reset to a named 10-second request timeout, all three named blocking lifecycle/socket calls run through `asyncio.to_thread`, and the real-contention integration test is synchronized on actual lock acquisition and proves both survival past the old one-second deadline and absence of the measured event-loop starvation. The full M10 sweep nevertheless found two remaining async-boundary defects, one introduced by moving socket work into cancellation-insensitive worker threads and one pre-existing synchronous filesystem path, so I would not ship this version yet.

**Findings:**

1. [BLOCKER] `zikaron/mcp/connection.py::ServiceConnection.request` awaits `_send_request` and `_read_response` through `asyncio.to_thread` while owning `self._lock`, but has no `asyncio.CancelledError` cleanup around either await. Cancelling an MCP tool task cancels the awaiting coroutine, not a worker function that is already running; `async with self._lock` then releases the lock while that worker can remain inside `socket.send` or `socket.recv`, and `self._sock` still points at the same socket. A later tool call can therefore acquire the lock and concurrently send on or read from that socket: two manual send loops can interleave request bytes, or the orphaned read can steal the later call's response. The same cancellation during `_connected_socket`'s `connect_start_if_absent` worker can discard a socket returned after its awaiter is gone without any deterministic close. Make worker ownership cancellation-safe: on cancellation of send/read, atomically detach `self._sock`, `shutdown`/close that exact socket to wake the worker, and re-raise cancellation so no later request can reuse it; run connection establishment as a retained/shielded task whose eventual returned socket is closed if its caller was cancelled. Add barrier-controlled tests that cancel while fake worker sends, receives, and establishes, then prove the lock is released only into a state where a subsequent request gets a fresh socket, no old worker consumes its response, and a late established socket is closed.

2. [BLOCKER] `zikaron/mcp/connection.py::_read_store_identity` still performs synchronous filesystem I/O directly on the event-loop thread: `db_path.exists()` calls `stat`, and `resolve_effective_config(store_dir)` reaches `core/config/resolution.py::_read_layer`, which calls `Path.read_bytes()` for both config layers. Thus the requested claim that no synchronous I/O remains reachable from an `async def` method's own thread is false, and a slow or stalled project/config filesystem still freezes every FastMCP coroutine before the now-correct threaded `connect_start_if_absent` even begins. Move the existence check and synchronous config resolution into `asyncio.to_thread` (preferably one helper returning absent-vs-config so the branch remains explicit), leaving only `Store.open`/`close`—already asynchronous through `aiosqlite`—on the loop. Add a focused test whose patched filesystem/config read blocks on a threading event while an unrelated coroutine continues to tick, mirroring the contention regression test's proof rather than only asserting that `to_thread` was called.

## Round 6 — 2026-08-03

**Summary judgment:** The two named filesystem/config calls are now offloaded, and the send/read handlers correctly detach the cancelled call's socket before the connection lock can be reused; under one cancellation, the shielded connection task's eventual socket is also collected and closed. I would still not ship: the full path retains synchronous permission I/O, connection cleanup itself is vulnerable to a second cancellation, plain `close()` does not provide the claimed worker wake-up, and cancellation can reset the consolidator takeover guard to a state that permits a second successful plan.

**Findings:**

1. [BLOCKER] `zikaron/mcp/connection.py::_read_store_identity` still reaches synchronous filesystem I/O on the event-loop thread through `await Store.open(...)`: `zikaron/core/store/store.py::Store.open` calls `permissions.enforce_existing_store_permissions(store_dir)` before its first `await`, and that helper runs `Path.is_symlink()` for every ancestor plus `is_dir()`, `stat()`, possible `chmod()`, and `is_file()`/`stat()` for the database, WAL, and SHM files. Offloading `db_path.exists()` and config resolution therefore fixes the two calls named in Round 5 but not the stated property that this identity path no longer stalls FastMCP's loop. Move the permission preflight itself off-loop (preferably inside `Store.open`, e.g. `await asyncio.to_thread(permissions.enforce_existing_store_permissions, store_dir)`, so every async caller gets the guarantee), and add a behavioral test that blocks that helper on a `threading.Event` while an unrelated coroutine demonstrably advances.

2. [BLOCKER] `zikaron/mcp/connection.py::ServiceConnection._connected_socket` protects `connect_task` only during the first await; after catching cancellation it does a bare `await connect_task`. A second `Task.cancel()` during that cleanup propagates into `connect_task`, marks its `asyncio.to_thread` task cancelled while the OS thread continues, and recreates the exact late-return leak: the worker may eventually return a connected socket to a cancelled future with no deterministic closer. Re-shield cleanup against subsequent cancellation (for example, loop on `await asyncio.shield(connect_task)` while preserving the original cancellation, then close the result), or install a retained completion callback that consumes failure and closes any result. Add a real double-cancel test. The current `tests/test_mcp_connection_cancellation.py::test_cancelling_while_establishing_a_connection_closes_the_eventually_returned_socket` does not exercise its claimed event release: it awaits the cancelled parent before setting `worker_may_proceed`, so the worker actually proceeds only when its five-second `Event.wait` timeout expires—explaining the reported ~5.5-second runtime—and cannot expose interrupted cleanup.

3. [BLOCKER] `zikaron/mcp/connection.py::ServiceConnection.request` detaches safely, but its send/read cancellation handlers call only `sock.close()`. Closing a descriptor in one thread is not a portable or guaranteed way to interrupt another thread already blocked in `send`/`recv`; the worker can remain alive until the 10-second socket timeout, and repeated cancellations can occupy the executor with orphaned workers even though later calls receive fresh socket objects. Abort the exact socket with best-effort `shutdown(socket.SHUT_RDWR)` before `close()` (while ensuring cleanup errors cannot replace the original `CancelledError`), and test with a real `socket.socketpair()` whose worker is blocked in `recv`, asserting cancellation wakes and terminates it promptly without a separate event manually releasing the fake operation. The present event-gated fakes ignore socket closure and therefore prove detachment, not the comments' stronger claim that the blocking syscall observes closure and exits.

4. [BLOCKER] `zikaron/mcp/consolidator.py::_PlanBridge.ensure_planned` does not handle `asyncio.CancelledError`. If `plan_groups` commits and the tool task is cancelled while its response read is still in flight, `ServiceConnection.request` re-raises cancellation and the bridge remains `UNPLANNED`; the next `zikaron_next_group` calls `plan_groups` again, allowing two successful takeovers from one client process despite M10's explicit at-most-once-successfully invariant. Catch cancellation around the in-flight planning request, move the bridge to terminal `FAILED` with a recorded transport/ambiguous-outcome error for later calls, and re-raise the original cancellation; add a barrier-controlled test that cancels after the fake service records a successful plan but before the response is delivered, then proves a subsequent call cannot issue another plan.

## Round 7 — 2026-08-03

**Summary judgment:** The permission preflight is now off-loop at the shared `Store.open`/`Store.create` boundary, repeated cancellation cannot abandon the retained connection task, and cancellation makes the consolidation bridge terminal before another takeover can be attempted; these are substantive fixes to three of Round 6's four findings. The remaining plain-`close()` behavior is a real but bounded operational risk, not a load-bearing correctness gap for this Linux-only local client: detachment prevents socket reuse or response theft, and the established socket timeout bounds a stranded send/receive worker to roughly ten seconds, although enough rapid cancellations could temporarily consume the default executor. After seven rounds, that bounded exceptional-path delay is proportionate to disclose and accept for human operator review rather than block M10.

**Findings:**

1. [NITPICK] `zikaron/mcp/connection.py::ServiceConnection.request` cancellation comments (the blocks immediately above the `_send_request` and `_read_response` awaits), plus `tests/test_mcp_connection_cancellation.py::test_cancelling_during_send_closes_the_socket_so_a_later_call_gets_a_fresh_one`, still say or imply that `sock.close()` makes the worker's blocked syscall observe closure and exit. Do not rely on that part of the residual-risk rationale: on Linux, closing a descriptor from another thread is not a reliable wake-up mechanism for an already-blocked `recv`/`send`; the in-flight syscall may retain its reference to the underlying open file description until data, peer closure, or timeout, while `shutdown(SHUT_RDWR)` is the usual explicit wake-up. Correct these comments to state the guarantee the implementation actually provides—immediate detachment and no reuse, with worker exit bounded by `_REQUEST_TIMEOUT_SECONDS`—and optionally add a repeated-cancel regression test. This is documentation/test precision, not a shipping blocker: the ten-second socket timeout supplies the boundedness that makes the accepted risk defensible even when `close()` does not wake the syscall.
