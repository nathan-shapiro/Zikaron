## Round 1 — 2026-10-13

**Summary judgment.** The transaction diagnosis is correct against the code and against SQLite: `sqlite3BtreeBeginTrans` invokes the busy handler only while the connection holds no transaction, so a deferred `BEGIN` that has read is refused at once on its first write whatever `busy_timeout` says, and every corpus-database transaction site the brief names (`scan.py`, `disposal.py`, `repair.py`, `counters.py`, `database.py`, `lifecycle.unlock`) is classified consistently between §6.2, `architecture.md` and invariant 18. K14's grammar, persistence rule, fallback and state table are precise enough to build from. What is missing is two perturbation cells — the plan in `FINDINGS.md` §"Current state" promised a perturbation table for the migration and none is in the artifacts — and each turns a stated guarantee false: a `refresh` that arrives between a spawned build's lock release and its process exit is silently lost, and a corpus migration ungated by `memory.db`'s version produces exactly the corpus-by-corpus refusal that D37's amendment says version 4 prevents. Both are a paragraph each to fix. The rest is improvements a build would otherwise have to decide for itself.

### Findings

1. **[BLOCKER] `already_indexing` keyed on process liveness alone loses a `refresh` that arrives while a finished build is still exiting, and makes `refresh --wait` fail there.**
   Where: `design/build-plan.md` §M39 "What ships" item 2 (*"answers `already_indexing` while one is alive … whether or not it has taken the lock"*) and "Invariants and properties" → "One spawn"; `design/knowledge-index.md` §8.4 ¶"A build is under way from its spawn" and the `already_indexing` row of its outcome table; §13 invariant 19.
   The spec is already inconsistent with itself on this point: the §8.4 table row says *"one this service spawned for the corpus is still alive **and has not yet taken it**"*, while invariant 19 and the brief say *"whether or not that one has yet taken the lock"*. The second reading has a hole. `lifecycle.refresh` (`core/knowledge/lifecycle.py:313–317`) releases the lock in `scan.run`'s `finally`, then **reopens the corpus** for `reporting.observe`, then `indexer/main.py:build` prints its report and the interpreter tears down the encoder and the `aiosqlite` worker threads — a window of hundreds of milliseconds after the lock is gone during which the process is alive, longer under load. A `refresh` landing there is answered `already_indexing` and spawns nothing, so an agent that writes documents, refreshes a small corpus, writes more and refreshes again has its second refresh silently discarded as *"the idempotent case"*. Worse for `--wait`: the baseline read sees no lock (released) and the finished build's mark; the brief's rule then takes *both halves* of the predicate, the mark never advances, and `_await_builds` (`knowledge/main.py:483–485`) reports *"no build started within 30s"* and exits 1 for a corpus that is built and `ok`. The brief's CLI rule is right; it is the service's rule that is too wide.
   Fix — in §8.4, invariant 19 and brief item 2, make a spawned process evidence only until the build shows itself by its lock: *"The service keeps, per corpus **id**, the process it last spawned for it and the instant it spawned it. `refresh` and `add` answer `already_indexing` while that process is alive **and the corpus's `last_scan_started_at` is still absent or older than that instant** — a build that has not yet shown itself by its lock. Once the mark has passed the spawn instant the build has taken its lock, the lock governs as it always has, and the entry is dropped; a dead process is dropped at the next look."* Then the §8.4 table row's *"has not yet taken it"* is the rule and invariant 19 should say the same. Add the missing test cell under "One spawn": *a spawned build that has released its lock and is still exiting answers `started` to the next `refresh` and spawns.* Also state what `refresh` tells the caller in that case is unchanged.

2. **[BLOCKER] Corpus migration is not gated on `memory.db`'s version, so an upgraded indexer spawned by a still-running old service migrates corpora the old service then refuses — the outcome version 4 exists to prevent.**
   Where: `design/knowledge-index.md` §7.7.1 ¶1 (*"brought forward by whichever process opens it to read or write it"*); `design/schema.md` §"When the version moves" ¶"A knowledge-base database's schema moving…" (*"a binary that cannot read the corpora refuses the store whole, at its version, rather than opening it and failing on its corpora one at a time"*); D37's amendment in `design/overview.md` and `FINDINGS.md`; the brief's ¶"What landing in this tree does".
   The path: `distribution.md` §3 says *"Upgrading does not replace a running service"*. The old service (0.3.2 code, in memory) answers a `refresh` by `detach.spawn` → `sys.executable -m zikaron.knowledge.indexer` → **the new code on disk**. That build opens `memory.db` through `scope.open_store`, which never passes `migrate` (version stays 3, which the new binary supports), then `KnowledgeDatabase.open` brings the corpus to schema 2 as §7.7.1 directs. The old service's next `search`/`list`/`status` on that corpus hits `_schema_too_new` (`database.py:378`) → `state: "error"`, `refresh` → `unreadable`, `remove` preview → `chunks: null`, until somebody restarts the service — and nothing says why. So a version-3 store **can** hold a schema-2 corpus, which is the contrapositive of the sentence schema.md adds, and the brief's *"its next service start … migrates its store to version 4 and its two corpora to schema 2"* names the wrong first mover: in `~/Trading/LeibaTrader` the first mover after the merge is the first build the running service spawns.
   Fix: *"A corpus is brought forward only by a process that opened `memory.db` at version 4 or later"* — the service after its own startup migration, and any build whose `OpenStore.schema_version` says so (that value already exists for the `knowledge_build` row's gate, `schema.md` §"Migration posture"; same pattern). `KnowledgeDatabase.open` takes `migrate: bool` as `Store.open` does. A build below the gate builds the corpus at schema 1: it writes no link columns and skips item 6's re-read, and search's fallback covers its rows — the behaviour §7.7.1 already specifies for a previous-version build. Amend §7.7.1 ¶1, schema.md's paragraph (add *"and a version-3 store never holds a schema-2 corpus"*), the D37 row and FINDINGS line, and the brief's "What landing" paragraph. Add the test cell: *a build against a version-3 store leaves a schema-1 corpus at schema 1 and builds it; the same corpus opened by a version-4 service migrates.*

3. **[IMPROVEMENT] §7.7.1 overstates what a previous-version build survives, and the migration's cost on the request path is unstated.**
   Where: §7.7.1 ¶"A build of the previous version can still be running across the upgrade" (*"Its writes keep working, since every statement it issues names its columns"*), and its "What can move under a link" table.
   Column naming is right, but that build's per-file transactions are the **deferred read-then-write** §6.2 diagnoses, and the migration's `BEGIN IMMEDIATE` … `COMMIT` is a writer holding the lock: landing between the old build's `_stored_chunks` SELECT and its first DELETE it ends that build with `database is locked`, leaving `reindex_required` and no completion instant — the §1 signature in `research/build-transaction-upgrade-race.md`. Recovery is one refresh, so this is a row to add rather than a rule to change: *"the migration commits between a previous-version build's read and its write → that build ends as §6.2 describes; its committed files stay, the next build resumes."* Same paragraph: say what the migration costs and who pays — four `ALTER TABLE ADD COLUMN`s, four `meta` inserts and one bounded read (the first `LINK_PREFIX_BYTES` of each file's chunks) per `files` row, under the write lock, inside the **first request that opens the corpus after the upgrade**, which may be a search with a latency budget.

4. **[IMPROVEMENT] "Every source of one search in one invocation" cannot raise the link counters where §12 says counters are raised.**
   Where: §7.7 ¶"The hash" (*"every source of one search in one invocation"*); brief item 8 (*"raises the four link counters by the rules §12 gives the others"*); §12.
   `counters.record_search` runs inside `groups._serve` per corpus while that corpus is open (`groups.py:307–324`), before cross-KB assembly and before §8.7's shedding, so `results_returned` counts what the corpus answered. One git invocation per *search* means the states are known only after every group is closed, so the link counters would need a second best-effort transaction per corpus, reopening it — or a different basis from the other four. State the resolution: *one invocation per group that returned a linked result*, states computed inside `_serve`, the four link counters riding the same best-effort write as the group's others. Cost is ≤ one `git hash-object` per such group, ~3 ms each (§7.7's own figure), not one per search; say so where the 3.0 ms figure is quoted.

5. **[IMPROVEMENT] A batch `git hash-object --stdin-paths` dies on the first path it cannot open, and the spec does not say what the other sources then report.**
   Where: §7.7 ¶"There is no containment check…" and ¶"The hash"; brief item 7 (*"a source swapped for a FIFO between the two is what the timeout is for"*).
   git opens each path with `xopen` and dies (`fatal: could not open …`) on failure, after printing the hashes it had already produced. A source deleted between the `stat` and the invocation therefore fails the batch, and §7.7's `unverifiable` row (*"the hashing failed"*) reads as *every* linked result of that search going `unverifiable` for one vanished file. Decide it once: *"a batch git refuses is run again, once, over the sources that still pass the regular-file check; what then fails is `unverifiable`"* — or, if the author prefers the simpler rule, say explicitly that one failure marks the whole batch.

6. **[IMPROVEMENT] `LINK_PREFIX_BYTES`, `LINK_SOURCE_MAX_BYTES` and `LINK_HASH_TIMEOUT_SECONDS` have no values and no stated home.**
   Where: §7.7 ¶"The front matter, exactly", ¶"There is no containment check…"; brief items 3 and 7; §10 (which does not list them).
   The prefix bound is part of the **writer-facing** contract — a front matter that closes one byte past it is *declared and malformed* if a key preceded the cut, and *no link* otherwise — so a document writer (M40's generator, or a person) must be able to rely on a number, and the build must not pick one. Propose: `LINK_PREFIX_BYTES = 4096`, `LINK_SOURCE_MAX_BYTES = 8 MiB`, `LINK_HASH_TIMEOUT_SECONDS = 2.0`; state in §7.7 that all three are implementation constants and not configuration keys, and list the prefix bound among what `README.md` owes a writer (brief item 11 already owes the format).

7. **[IMPROVEMENT] Brief item 5's last sentence names the wrong number as the operator's.**
   Where: `design/build-plan.md` §M39 "What ships" item 5: *"The version number itself is the operator's to set."*
   Every artifact fixes `memory.db` at schema 4 (`schema.md`, D37, FINDINGS, §7.7.1), so a build reading this could leave `CURRENT_SCHEMA_VERSION` unset waiting for a decision that is already taken. Replace with: *"`CURRENT_SCHEMA_VERSION` becomes 4 in this milestone; the release number the schema bump forces (`0.4.0`) is the operator's to set in the tagged commit (`CLAUDE.md` §"How this project works")."*

8. **[IMPROVEMENT] `remove` should see a spawned-and-lockless build the way `refresh` now does.**
   Where: §8.4 ¶"`remove`, after `confirm=true`…" (*"If an indexer holds the KB's lock, `remove` refuses"*); `lifecycle.remove`'s accepted check-then-act window.
   Once the service holds the spawned process per corpus (finding 1), a `remove` arriving in the model-load window can be refused `knowledge_base_busy` at no cost, closing that window for every build the service started rather than leaving it to a build that then fails on a dangling corpus. One sentence in §8.4 and one test.

9. **[NITPICK] Key the spawned-process table by corpus `id`, not name.** `rename` changes the name while a build may be alive (`lifecycle.rename` touches no file); a name-keyed entry would miss the renamed corpus and spawn a second build. Brief item 2 says "per corpus"; say "per corpus id".

10. **[NITPICK] `schema.md` §"When the version moves": *"marks a store last served by a build whose corpus databases are at schema 2"*** — it is the service, not a build, that moves `memory.db`; write *"last opened by a service whose corpus databases are at schema 2"*.

11. **[NITPICK] §7.7 ¶"What is read is persisted…": *"whose concatenation in `part_index` order is the file's leading bytes exactly (invariant 16)"*.** `chunks.text` is decoded text with the byte-order mark stripped (`text.sniff` decodes `utf-8-sig`), so the concatenation is the file's leading *characters* less any BOM, and the equality the brief's property test asserts holds because the grammar allows an optional BOM and an indexed file is valid UTF-8. Say that, so the implementer writes one reader over bytes and re-encodes the chunk text rather than wondering why the BOM case differs. In the same place, state that the migration's backfill and item 6's re-read both write `link_read_from = content_hash` — item 6 says it for the build and item 4 does not for the migration.

## Round 2 — 2026-10-13

**Summary judgment.** Every round-1 finding is applied and the applications hold against the code: `scan._begin` writes `last_scan_started_at` in the lock's own `IMMEDIATE` transaction, so the mark rule in §8.4 and invariant 19 is sound; `chunking.split_lines` partitions on `\n` alone with terminators kept, so the stored chunks' concatenation is the decoded text exactly and the one-reader claim in §7.7 is true; the migration gate on `OpenStore.schema_version` closes the LeibaTrader path, and nothing on the service's knowledge path imports lazily, so the "old code in memory" premise of §"What landing" is real. What remains is narrower than round 1 and is mostly about three cells the artifacts still do not decide — the `--wait` predicate when the service cannot say *which* `already_indexing` it answered, two refresh requests interleaved on one event loop, and the schema-2 reader meeting a schema-1 corpus it is not allowed to migrate — plus a cost bound the migration measurement needs a pass criterion against. None is a redesign; each is a paragraph and a test cell, and the brief should carry them before a build starts rather than after its first review round.

### Findings

1. **[IMPROVEMENT] §9 and the brief give two different `--wait` rules for `already_indexing`, and neither is decidable from what the service sends.**
   Where: `design/knowledge-index.md` §9 ¶"The predicate is not…" (*"**One the service reported running before it took its lock** … takes both halves"*); `design/build-plan.md` §M39 item 2 (*"for a corpus whose lock was not held when its baseline was read"*); `zikaron/service/serialize_knowledge.py:181–189` (a refresh entry is *"each corpus's summary plus an `outcome`"* — no `lock`); `zikaron/knowledge/main.py:310–346, 402–488`.
   §9's sentence presumes the CLI can tell a spawn-based `already_indexing` from a lock-based one, and the outcome value is the same string for both. The brief substitutes the baseline's lock as a proxy, which is the right shape — *always both halves* would hang the ordinary provisioning case, where `refresh --wait` lands after `add`'s build took its lock, until the 30 s appearance deadline and then exit 1 — but the proxy has a hole in each direction: a baseline that saw build X's live lock, X releasing and *another client's* refresh spawning Y in the milliseconds before this call reaches the service, answers `already_indexing` for lockless Y, the CLI takes the lock half alone, its first poll sees no lock, and it returns 0 with Y about to build; the mirror (no lock at baseline, X taking its lock before the call) happens to be safe only because X's mark differs from the baseline. Decide it with one keyable field rather than a proxy: **the refresh response's `already_indexing` entry carries `lock` exactly as `status` reports it — `null` for a build this service spawned that has not reached its lock** — and `--wait` takes the lock half alone when that `lock` is live and both halves otherwise. Amend §8.4's outcome table row, §9's sentence and brief item 2 to the same words, and add the cell to the "One spawn" bullet: *an `already_indexing` whose `lock` is `null` is waited for until its mark advances and its lock is gone; one whose `lock` is live is waited for until the lock is gone.* If the author prefers to keep the wire shape, then at minimum rewrite §9's sentence to state the baseline-lock proxy the brief uses, so the spec and the brief name one rule.

2. **[IMPROVEMENT] Two `refresh` requests for one corpus interleaved on the event loop both spawn, and nothing in the spec or the test list forbids the implementation that lets them.**
   Where: `design/knowledge-index.md` §8.4 ¶"A build is under way from its spawn…"; §13 invariant 19; `design/build-plan.md` §M39 item 2 and "One spawn"; `zikaron/service/dispatch_knowledge.py:336–359` (`_spawn`, synchronous) and `397–422` (`knowledge_refresh`: `await builds.plan(...)` then `_spawn`).
   `knowledge_refresh` is `Access.READ`, so two requests for one corpus — an agent's `refresh()` sweep beside a CI step's `refresh --wait`, or two sessions — run concurrently on the loop. The table lives in the service and `core/` may not hold process state, so the check must be in `dispatch_knowledge`; the two natural placements both race. Checking after `plan` and then `await`ing anything before the `Popen` — including a fresh read of `last_scan_started_at` to record *"as it stood at the spawn"*, which the spec's wording invites — lets both requests pass the check before either spawns. Consequence is bounded by item 1 (the loser is refused at its lock, one model load wasted) but invariant 19 is then false under an ordinary load, and the named test (`add` then `refresh`) cannot see it. State the rule in §8.4 and item 2: *the mark recorded is the one `plan`'s own observation read — no second read — and the check against the table, the spawn and the record are one step with no `await` between them, so two requests for one corpus cannot both spawn.* Add the cell: *two `knowledge_refresh` for one corpus dispatched concurrently spawn one build and answer one `started` and one `already_indexing`.*

3. **[IMPROVEMENT] A schema-2 reader that meets a schema-1 corpus it may not migrate is told what not to *write* and nothing about what not to *read*.**
   Where: `design/knowledge-index.md` §7.7.1 ¶"The gate…" (*"it writes no link columns and re-reads nothing"*); §11's schema-1 row; `design/build-plan.md` §M39 item 4 and "The gate"; `zikaron/core/knowledge/files.py:26, 87` (`_COLUMNS`, `load_all`), `zikaron/core/knowledge/reporting.py:285–306` (`gather`, which item 9 extends with `files_linked`), `zikaron/knowledge/indexer/main.py:115` (`builds.prepare` → `reporting.observe` → `gather`, inside the build).
   A version-3-store build runs `observe` before it builds and `files.load_all` in its walk phase; if either names a link column — `SELECT … link_read_from …`, `COUNT(*) WHERE link_declared = 1` — the build dies with `no such column` on the first corpus it meets, which is every corpus on the upgrade path §"What landing" describes. "The gate" test would catch the walk-phase case; nothing names the `status`-shaped read, and a build that passes the test by special-casing `load_all` ships `gather` broken for the next reader. State the rule once, in §7.7.1 beside the write-side one: *every read of the four link columns is conditional on the corpus's recorded `schema_version`; at schema 1 `files_linked` is `null`, no link column is named, and a search would treat every row as the fallback case (it never does: a version-4 service migrates or reports `error`).* Extend "The gate" to: *…builds it, and its own `status` observation of that corpus names no link column.*

4. **[IMPROVEMENT] The migration's cost has a measurement and no pass criterion, and the table omits the cell the criterion exists for.**
   Where: `design/knowledge-index.md` §7.7.1 ¶"What it costs, and who pays" and the table row *"a new service while a previous-version build still runs"*; `design/build-plan.md` §M39 item 4 (*"The migration's cost on a real corpus is measured, and the figure goes in `research/`"*); `zikaron/core/knowledge/ddl.py:19` (`BUSY_TIMEOUT_MS = 5000`).
   The row covers a *previous-version* build, whose deferred transactions the migration's commit ends. The LeibaTrader path produces a different cell: a **current-version** build, spawned by the old service and therefore built at schema 1, still running when the restarted service's first search migrates the corpus under it. That build's per-file `BEGIN IMMEDIATE` now waits under SQLite's 5 s `busy_timeout` for the migration's whole transaction — four `ALTER`s plus one chunk-prefix read per `files` row, in one transaction by design — and a migration longer than that ends the build exactly as §6.2's defect did. So the measured figure has a bar whether or not one is written: `FINDINGS.md` §"How the next review should be briefed" asks what you would do at each side of it. Write it: *measured on the largest real corpus, the migration must hold the write lock well inside `BUSY_TIMEOUT_MS`; if it does not, the backfill leaves the schema step — columns, counters and `schema_version` in one transaction, every row's `link_read_from` `NULL` — and the rows are covered by the fallback §7.7 already specifies and made exact by the next build (§7.7.1), at the cost of `files_linked` being inexact until then.* Add the row: *a current-version build built at schema 1 is running when a version-4 opener migrates the corpus → the build waits `busy_timeout` for the migration's commit; its later rows lack a link record and are read by the fallback, then by the next build.* And say who else pays: the first `knowledge_list` or `status` after the upgrade opens every corpus (`reporting.list_bases`), so the triage call §8.5 prices at single-digit milliseconds pays every corpus's migration at once, serially.

5. **[IMPROVEMENT] `LINK_HASH_TIMEOUT_SECONDS` is per call and calls are per corpus, so a search's worst case is `5 s × corpora` against a client timeout of 10 s.**
   Where: `design/knowledge-index.md` §7.7 ¶"There is no containment check…" (*"each hashing call runs under `LINK_HASH_TIMEOUT_SECONDS` = 5"*) and ¶"The hash" (*"once per corpus whose results include a linked one"*); `zikaron/mcp/connection.py:64` (`REQUEST_TIMEOUT_SECONDS = 10.0`); `zikaron/service/dispatch_knowledge.py:241–257`.
   The 5 s is sized to the 64 MiB cap (twenty such sources through git is a few seconds warm), which is fine for one corpus. A store with three or more corpora of linked documents whose sources are slow — a network mount, a cold cache, one FIFO swapped in per corpus — spends more than the client's 10 s and the *whole search* fails rather than its link states, which inverts §7.7's promise that a bad source costs `unverifiable` and nothing else. Make the bound one per search: *`LINK_HASH_TIMEOUT_SECONDS` bounds all hashing one search does, across corpora, from the first call; a corpus whose call starts after the budget is spent reports every linked result `unverifiable` without running git.* State beside the 3.0 ms figure that the worst case is then one timeout per search, not per corpus.

6. **[IMPROVEMENT] A git that is installed and refuses to answer at all is not a case the spec covers, and it is the devcontainer case.**
   Where: `design/knowledge-index.md` §7.7 ¶"The hash" (*"Where git is not installed the same blob form is computed in-process"*) and ¶"A batch git refuses is run once more…".
   The second run is specified for a per-path failure. A `git hash-object` that dies before hashing anything — `fatal: detected dubious ownership` when the Zikaron root is owned by another uid, as it is inside the containers §6.2 already names as ordinary; a corrupt `.git` — fails both runs identically, so every linked result of every corpus reads `unverifiable` permanently, with nothing saying why, in exactly the environment M40's producer would run in. Decide it once: *a call that exits non-zero having printed no hash is git being unavailable for this search, and the in-process form is used as when git is absent; a call that printed some hashes and died is the per-path case and gets the second run.* The in-process form is what git itself prints from a directory it does not recognise as a work tree, so the answer is the one a producer running in the same container would have recorded.

7. **[IMPROVEMENT] The grammar says "line" and "exactly `---`" without saying what a line is, and the test list names `\r\n`.**
   Where: `design/knowledge-index.md` §7.7 ¶"The front matter, exactly" (*"begins with `---` and a line terminator; the block ends at the next line that is exactly `---`"*); `design/build-plan.md` §M39 "The grammar" bullet; `zikaron/core/knowledge/chunking.py:31–37` (`LINE_END = "\n"`, `\r` kept as part of the line).
   The chunker splits on `\n` alone, deliberately not `str.splitlines`, so in a `\r\n` file the line is `---\r` and a reader written with `splitlines()` disagrees with one written against the chunker about where lines fall — and about whether a form feed or U+2028 ends one. Fix the grammar to the chunker's rule: *lines are split on `\n` alone; one trailing `\r` is removed from a line before it is compared with `---` or read for a key, and nothing else is a terminator.* Then "exactly `---`" means after that removal and with no other whitespace, which the test bullet should say.

8. **[NITPICK] `source.path` is `null` on two different conditions in two places.** §7.7 ¶"What a result carries" says *"`null` where it did not parse"* (per value) and §3.2's column comments say `source_path`/`source_blob` are written *"where the declaration is well-formed"* (whole declaration). A key present with a parseable path beside a malformed hash is `null` under one reading and the path under the other. Pick §3.2's — the columns are written only for a well-formed declaration — and reword §7.7 to *"or `null` where the declaration is malformed"*.

9. **[NITPICK] What `holder` names for a spawned-and-lockless refusal is unspecified.** `knowledge_base_busy`'s payload carries `holder=error.holder.describe()` (`dispatch_knowledge.py:196–201`) and `already_indexing` an `IndexerBusyError` built from a `LockHolder`; the spawned case has no lock rows. Say in §8.4 that the service reports the spawned process's pid, this host and the spawn instant as the holder, so the message a person reads names the build rather than an empty holder.

10. **[NITPICK] `zikaron_knowledge_refresh`'s description still prices `already_indexing` as "one lock check".** §8.4 "Tool descriptions" (*"`already_indexing` (one already was, so this call queued nothing and cost one lock check)"*). After item 2 it is also a build the service spawned and is still loading, and the cost is no longer a lock check. Add the sentence to brief item 11's owed list and propose: *"`already_indexing` (one already was — running, or started by an earlier call and still loading — so this call queued nothing)"*.

11. **[NITPICK] `design/schema.md` §"When the version moves": *"marks a store last opened by a service whose corpus databases are at schema 2"*** contradicts the same paragraph's *"a version-4 store can hold schema-1 corpora for a while"*. Write *"last opened by a service that brings corpus databases to schema 2"*.

12. **[NITPICK] The one registration function for a connection's transaction mode has the wrong contract for the build's connection.** Brief item 1 says *"set once on the build's connection … waiting for the write lock under that connection's `busy_timeout`"*; `zikaron/core/store/holders.py:114–123` — `hold(db, immediate=True)` is the only public registration, it sets `polls_for_lock=True`, and its docstring requires `busy_timeout = 0`, which the corpus connection is not at (§3.2 keeps 5 s). An implementer who reaches for it gets SQLite's 5 s wait *inside* the primitive's 5 s poll. Say in item 1 that the build sets the holder's `immediate` and leaves `polls_for_lock` off — or that `hold` grows the parameter — so the one `BEGIN IMMEDIATE` mechanism the brief describes is the one that exists.
