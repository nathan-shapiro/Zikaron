## Round 1 — 2026-08-02

**Summary judgment:** The implementation is unusually coherent: both arms, RRF, the total order, supersession repair, transaction-scoped instrumentation, and the structured search/push outputs closely match the revised design, and the claimed check, integration, coverage, and mutation gates are the right kinds of verification. It is not ready to ship because the query preflight can still permit silent model truncation under a legal non-default prefix, and several guards advertised as structural do not enforce the full contracts they describe. The verification claims do not cover that tokenizer-boundary case, exact semantics for all five consumer scopes, or impossible skipped-arm states.

**Findings:**

1. **[BLOCKER] The dense preflight does not prove that the actual assembled model input fits.** `zikaron/core/retrieval/query.py:253-260` separately counts `prefix` and `text`, selects a head from the query-only tokenization, and then embeds `prefix + kept` without counting that concatenated string. Tokenization is not generally additive across a configurable string boundary, especially when a legal custom `embed_prefix_query` has no trailing tokenizer boundary; therefore `count(prefix) + count(query) <= cap` does not imply `count(prefix + query) <= cap`. A short query can be recorded as `query_truncated=False`, or a nominally truncated head can be recorded as safely bounded, while the deployed tokenizer/model silently truncates the assembled input—the exact failure this preflight exists to prevent. `tests/test_retrieval_integration.py:110-118` checks the assembled count only for the default trailing-space prefix and does not make production enforce it. Amend `design/retrieval.md` §“The dense arm” to require an assembled-input check, then make `external_query()` count `prefix + kept` plus special tokens before embedding; shrink on query token boundaries until it fits (and set `query_truncated` from what was actually kept), or report `BAD_CONFIG` if the prefix leaves no query token. Add a boundary-sensitive fake-tokenizer regression using a legal non-default prefix where concatenated token count exceeds the sum of separate counts, covering both an otherwise-short query and the truncated-head path.

2. **[IMPROVEMENT] The consumer-filter guards do not establish the exact predicates the done-when condition claims.** `tests/test_retrieval_eligibility.py:91-110` checks only whether the strings mention `active` and/or `tier`; changing consolidation to `tier = 'journal'`, changing `active = 1` to `active = 0`, or changing the conjunction to a disjunction would still pass. The structural scan at `tests/test_retrieval_eligibility.py:212-231` recognizes only a short list of literal spellings, so an out-of-table filter such as `m.active IS TRUE` also evades it. Existing real-arm behavior tests exercise the base scope and dedup, but not the exact consolidation and orphan candidate sets (`tests/test_retrieval_arms.py:482-495`). Add a table-driven real-store matrix for every `Consumer`, with live/superseded/retired rows in both tiers plus the self row, and assert the exact UUID set through each arm (or the common `retrieve()` core). Keep the source scan only as a supplementary architecture guard, preferably AST/SQL-token based; do not use column presence as the semantic oracle.

3. **[IMPROVEMENT] `ArmOutcome` accepts impossible skipped states despite claiming to enforce them structurally.** `zikaron/core/retrieval/arms.py:99` returns as soon as both instrumentation fields are null, without requiring `rows == ()` or requiring the lexical arm; `ArmOutcome.skipped()` at `zikaron/core/retrieval/arms.py:134-141` also accepts any `Arm`, including `DENSE`. Thus a dense arm can be “skipped,” or a null/null outcome can carry fused rows, contradicting `design/retrieval.md`’s rule that only a zero-term lexical arm skips. `tests/test_retrieval_arms.py:63-69` verifies only the valid factory result and never proves malformed forms fail. In `__post_init__`, reject null/null unless `arm is Arm.LEXICAL` and `rows` is empty; make `skipped()` construct lexical directly rather than accept an arm; add tests for dense-null/null and null/null-with-rows rejection.

4. **[IMPROVEMENT] Retrieval event payloads bypass the binding “types, not dicts” rule and can drift silently at runtime.** `zikaron/core/retrieval/reads.py:123` returns `dict[str, object]`, and the three event producers at `reads.py:204`, `:236`, and `:279` build schema-defined payloads as untyped dictionaries. The shared sink accepts any `dict[str, object]` (`zikaron/core/records/memory.py:210`) and immediately serializes it (`memory.py:230`) without checking `EVENT_SPECS`. Exact-key tests catch the current literals but mypy cannot catch a renamed/mistyped field in production code, which is precisely the failure `design/coding-standards.md` §2 prohibits. Introduce frozen typed detail values for `Search`, `SurfaceCall`, and `Surface` (sharing a typed arm-termination value), and serialize/validate them centrally against their `EventKind`; make the logging boundary accept the typed event-detail union rather than an arbitrary dictionary.

5. **[IMPROVEMENT] Reviewed code contains circumstantial provenance explicitly forbidden by the binding standard.** `zikaron/core/retrieval/__init__.py:17` points to “`FINDINGS.md` open question 2,” `zikaron/core/retrieval/eligibility.py:7` cites a “round-1 corpus review,” and `tests/test_retrieval_arms.py:189` cites “Round 5.” `design/coding-standards.md` §5 says no review-round numbers or `FINDINGS` references in code, including comments/docstrings; these references will rot and the reasons are already expressible timelessly. Replace them with the underlying reasons only: tuning requires a measured sweep without reindexing; divergent predicates make consumers disagree; equality has no observed surplus and therefore cannot claim a cut.

VERDICT: NEEDS_CHANGES

## Round 2 — 2026-08-02

**Summary judgment:** The assembled-input blocker is fixed correctly: the implementation counts exactly what it embeds, preserves an already-fitting query byte-for-byte, shrinks only on real overflow, and refuses the one-token-floor failure. The exact lexical consumer matrix plus both arms' shared call to `Scope.where()` makes the unchanged literal source scan acceptable as an honestly framed supplementary tripwire; the skipped-state and provenance fixes are also complete. The event remedy is valuable defense in depth, but it still leaves the shipping retrieval payloads outside the binding typed-domain rule and permits malformed scalar values that its claimed shape validation does not inspect.

**Findings:**

1. **[IMPROVEMENT] Production event validation enforces keys and closed enums, not the payload's value types, so it is not yet a sufficient substitute for the required typed values.** `zikaron/core/events.py`, `EventSpec.validate()`, skips every value check when `DetailField.values` is empty (`if not field.values ...: continue`); consequently details such as `FETCH {"version": None, "found": "yes"}` or a `SEARCH` with `query_tokens="many"`, `query_truncated=0`, or `uuids="one-uuid"` pass validation. `zikaron/core/records/memory.py::log_event` still accepts `dict[str, object]`, while `zikaron/core/retrieval/reads.py::_arm_detail`, `search`, `_log_surface`, and `surface` still construct untyped dictionaries, so strict mypy cannot catch those substitutions. This is materially better than round 1—renamed keys, ordering drift, memory cardinality, and closed-set drift now fail for every kind—but it does not satisfy `design/coding-standards.md` §2's explicit “Every payload ... becomes a typed object” rule or its stated compile-time guarantee. Keep `EventSpec.validate()` as defense in depth, but introduce frozen typed detail values (preferably for all 15 current `EventKind`s in one repository-wide change), pair each value with its kind at the logging boundary, and serialize centrally; add negative tests for wrong scalar/container types and illegal nulls. This remains M5 debt because M5's three producers ship in this milestone; typing all current kinds is a coherent implementation scope, not a reason to exempt the newest three.

2. **[NITPICK] The new boundary-sensitive diagnostics and helper documentation claim more than the algorithm proves.** `zikaron/core/retrieval/query.py::_fit_to_cap` calls itself “The longest head,” but it starts at the separately computed `budget` and only searches downward; because the surrounding documentation correctly says boundary retokenization can reduce as well as increase the count, a `budget + 1` head can theoretically fit even when the full query does not. More importantly, `_prefix_leaves_no_query_token()` says assembly with “any single-token query” exceeds the cap and therefore “no query can be embedded,” while the loop tested only the current query's one-token head and boundary cost is query-text-dependent. `design/retrieval.md` §“The dense arm: a preflight,” the one-token-floor paragraph, makes the same universal implication. Preserve the current conservative head policy and `BAD_CONFIG` result, but describe `_fit_to_cap` as the nominal-budget head shrunk until safe, and change the error/design wording to say that this query's one-token head cannot fit beside the configured prefix; alternatively, search upward too if “longest head” is intended as an actual contract.

VERDICT: NEEDS_CHANGES
